### Teil 1: VL05 ab Folie 42 – Grundprinzipien und Kapselung

**Vier Grundprinzipien der OOP** (Folie 42): **Kapselung** (Objekt bestimmt selbst, wie sein Zustand geändert
wird), **Vererbung** („ist ein“), **Polymorphismus** (gleicher Aufruf, unterschiedliches Verhalten),
**Abstraktion** (Gemeinsames in eine Oberklasse, Details weglassen). VL05 behandelt nur Kapselung.

Einstiegsfrage: *„Wer darf eigentlich den Kontostand eines Kontos ändern?“* – Mit der Klasse aus VL05 Block 1 kann
jeder `anna.kontostand = -999` setzen. Kapselung: Die Klasse prüft selbst, das Objekt bleibt gültig, das Innere
kann sich ändern, ohne dass anderer Code angepasst werden muss.

**Sichtbarkeit Java ↔ Python:**

- `public` → `kontostand` (Standard, alles ohne Unterstrich ist öffentlich)
- `private`/`protected` → `_kontostand` – **nur Konvention**, Python prüft nichts
- package-private → gibt es nicht
- `__kontostand` → Name Mangling zu `_Konto__kontostand`, verhindert Namenskonflikte bei Vererbung, **kein Schutz**

**Keine Java-Getter/Setter für jedes Attribut.** Gibt es nichts zu prüfen, bleibt das Attribut öffentlich. Gibt es
Regeln, kommt eine **Property** dazu – eine Methode, die man von außen **wie ein Attribut** (ohne Klammern) benutzt.

```python
from decimal import Decimal

class Konto:
    def __init__(self, inhaber: str, kontostand: Decimal) -> None:
        self.inhaber = inhaber                 # frei änderbar → einfach öffentlich
        self._kontostand = Decimal(0)
        self.kontostand = kontostand           # nutzt schon den Setter → Regel gilt beim Anlegen

    @property
    def kontostand(self) -> Decimal:           # Getter:  anna.kontostand
        return self._kontostand

    @kontostand.setter
    def kontostand(self, neuer_wert: Decimal) -> None:   # Setter: anna.kontostand = x
        if neuer_wert < 0:
            print("Ungültig: negativer Kontostand.")
            return
        self._kontostand = neuer_wert

anna = Konto("Anna", Decimal("100.00"))
anna.kontostand = Decimal("-500")   # Ungültig: negativer Kontostand.
print(anna.kontostand)              # 100.00
```

Berechnete Property ohne eigenes Attribut (Folie 48): `jahresgehalt` = `monatsgehalt * 12`, bei jedem Zugriff neu.
Ohne Setter ist sie nur lesbar: `lena.jahresgehalt = 60000` → ty `Cannot assign to read-only property`, Laufzeit
`AttributeError`. Folie 49 merkt an: Üblich wäre bei ungültigen Werten `raise ValueError(…)` statt `print`.

**Attribut oder Property? (Folie 50)**

- frei änderbar → öffentliches Attribut (`self.inhaber`)
- nur lesen, ändern über Methoden → `_attribut` + Property **ohne** Setter (Bestand)
- ändern nur unter Regeln → `_attribut` + Property **mit** Setter (`kontostand`)
- berechnet → Property ohne eigenes Attribut (`jahresgehalt`)

Man kann mit einem öffentlichen Attribut anfangen und später eine Property daraus machen – der aufrufende Code
bleibt gleich. Interne Hilfsmethoden: `_pruefe_betrag()`.

**Weitere Java-Modifikatoren (Folie 51):** `static`-Variable → Klassenattribut; `static final` → Modulkonstante
`MAX_KONTEN: Final = 100`; `static`-Methode → meist normale Modulfunktion (`@staticmethod` gibt es); `final` →
`@final` aus `typing` (nur ty prüft); `abstract` → `abc.ABC`/`@abstractmethod` (VL06).

### Teil 2: VL05 – Zusammengesetzte Klassen, Module, `@dataclass`

**Hat-ein-Beziehung (Komposition):** Ein Objekt hat andere Objekte als Attribute (Konto hat Kunde, Bestellung hat
Kunde und Positionen). Jede Klasse bleibt klein.

```python
class Kunde:
    def __init__(self, name: str, ort: str) -> None:
        self.name = name
        self.ort = ort

class Konto:
    def __init__(self, kunde: Kunde, kontostand: int = 0) -> None:
        self.kunde = kunde                       # Konto HAT einen Kunden
        self.kontostand = kontostand

    def info(self) -> str:
        return f"{self.kunde.name}: {self.kontostand} Euro"

anna = Kunde("Anna Berger", "Heilbronn")
giro, spar = Konto(anna, 100), Konto(anna, 2500)
print(spar.info())               # Anna Berger: 2500 Euro
print(giro.kunde is spar.kunde)  # True – dasselbe Kunden-Objekt
```

**Module und Pakete (Folie 57):** Jede `.py`-Datei ist ein Modul; Ordner mit (gern leerer) `__init__.py` = Paket.
Kein `package`-Kopf wie in Java, mehrere Klassen pro Datei erlaubt. `from banking.konto import Konto`.

**`@dataclass` (Folie 58):** erzeugt aus den annotierten Attributen `__init__`, `__repr__` und `__eq__`.

```python
from dataclasses import dataclass

@dataclass
class Kunde:
    name: str
    email: str

k = Kunde("Anna Berger", "anna.berger@example.com")
print(k)          # Kunde(name='Anna Berger', email='anna.berger@example.com')
print(k == Kunde("Anna Berger", "anna.berger@example.com"))   # True  (Werte)
print(k is Kunde("Anna Berger", "anna.berger@example.com"))   # False (zwei Objekte)
```

Von Hand bräuchte man dafür `__eq__` mit `isinstance`-Prüfung und `return NotImplemented` (Folie 58, linke
Seite). Faustregel: `@dataclass` für **Daten** (Kunde, Adresse, Position), normale Klasse für **Verhalten und
Regeln** (Konto, Warenkorb, Lager). Auch Datenklassen dürfen Methoden haben. Zum Schluss: OOP-Vor-/Nachteile
und Geschichte (Simula 1967, Smalltalk, C++, Java 1995, Python 1991) – Details in Notiz 5.

### Teil 3: VL06 – Vererbung und `super()` (Folien 1–17)

Einstiegsfrage: *„Was ist Vererbung nochmal?“* – Eine **Unterklasse** übernimmt Attribute und Methoden einer
**Oberklasse** und kann ergänzen und ändern. Nur bei **„ist ein“** (Sparkonto ist ein Konto); für „hat ein“ →
Attribut (VL05).

```python
class Sparkonto(Konto):                          # Konto = Oberklasse (Java: extends)
    def __init__(self, inhaber: str, kontostand: int, zinssatz: int) -> None:
        super().__init__(inhaber, kontostand)    # Konto-Teil anlegen – PFLICHT bei eigenem __init__
        self.zinssatz = zinssatz

    def zinsen_gutschreiben(self) -> None:
        self.einzahlen(self.kontostand * self.zinssatz // 100)   # geerbte Methode

anna = Sparkonto("Anna", 1000, 2)
anna.einzahlen(500)
anna.zinsen_gutschreiben()                       # +30
print(anna)                                      # Konto von Anna: 1530 Euro (__str__ geerbt)
print(isinstance(anna, Konto), type(anna) is Konto)   # True False
```

- `super().__init__(…)` vergessen → Python ruft den Oberklassen-Konstruktor **nicht** von selbst auf (anders als
  Java). Fehler erst beim ersten Zugriff: `AttributeError: 'Sparkonto' object has no attribute 'kontostand'`;
  **ty meldet nichts**.
- Kein eigenes `__init__` in der Unterklasse → das der Oberklasse wird geerbt.
- `isinstance` prüft Klasse **und** Oberklassen; `type(x) is K` nur die genaue Klasse; `issubclass(Sparkonto, Konto)`.

### Teil 4: VL06 – Methoden überschreiben (Folien 18–29)

```python
from typing import override

class Girokonto(Konto):
    def __init__(self, inhaber: str, kontostand: int, dispo: int) -> None:
        super().__init__(inhaber, kontostand)
        self.dispo = dispo

    @override
    def abheben(self, betrag: int) -> bool:      # gleicher Name, gleiche Parameter
        if betrag > self.kontostand + self.dispo:
            print("Abgelehnt: Der Dispo ist ausgeschöpft.")
            return False
        self.kontostand -= betrag
        return True

    @override
    def __str__(self) -> str:                    # ergänzen statt ersetzen
        return f"{super().__str__()} (Dispo {self.dispo} Euro)"
```

- **Überschreiben:** Unterklasse definiert Methode mit gleichem Namen/Parametern → ersetzt die Version der
  Oberklasse für ihre Objekte. `super().methode()` ruft die Oberklassen-Version auf (ergänzen).
- **Methodensuche (MRO):** erst Klasse des Objekts, dann Oberklassen, zuletzt `object`
  (`Girokonto.__mro__` → `Girokonto, Konto, object`).
- **`@override`** (aus `typing`): ty meldet `invalid-explicit-override`, wenn nichts überschrieben wird (Tippfehler
  `abhebn`). Python selbst ignoriert die Markierung. Gegenstück `@final`.
- **Überladen ≠ Überschreiben:** Überladen (gleiche Klasse, andere Parameter) gibt es in Python nicht – die zweite
  `def` ersetzt die erste; Überschreiben (Ober-/Unterklasse, gleiche Parameter) ja.
- In Python gibt es pro Objekt **nur ein** Attribut eines Namens – Ober- und Unterklasse schreiben in dasselbe
  (kein Shadowing wie in Java).

### Falls noch Zeit ist: VL06 Polymorphie und abstrakte Klassen (Folien 30–47)

- **Polymorphie:** `kasse(zahlungsart: Zahlungsart, betrag)` ruft `zahlungsart.bezahlen(betrag)` – Kreditkarte,
  Rechnungskauf … reagieren unterschiedlich; neue Unterklassen ohne Änderung an `kasse()`. Typangabe bestimmt, was
  ty erlaubt; das Objekt bestimmt, welche Methode läuft. **Duck Typing:** Python prüft nur, ob die Methode da ist.
- **`object`** ist Wurzel jeder Klasse; `__str__` aus VL05 war schon ein Überschreiben.
- **Abstrakte Klasse:** `class Zahlungsart(ABC)` mit `@abstractmethod def bezahlen(...)`; `Zahlungsart()` →
  `TypeError: Can't instantiate abstract class …`. Unterklasse ohne alle abstrakten Methoden bleibt abstrakt.

## Wichtige Begriffe

- **Kapselung** – Objekt schützt seinen Zustand, ändert ihn nur nach eigenen Regeln
- **`_attribut`** – Konvention „intern“, kein Zugriffsschutz
- **Name Mangling** – `__x` wird zu `_Klasse__x`, gegen Namenskonflikte, kein Schutz
- **Property** – `@property` (Getter) / `@name.setter` (Setter); von außen wie ein Attribut, ohne Klammern
- **Read-only-Property** – Property ohne Setter; Zuweisung → `AttributeError`
- **Berechnete Property** – liefert jedes Mal einen neu berechneten Wert (`bruttopreis`, `jahresgehalt`)
- **Hat-ein-Beziehung / Komposition** – Objekt als Attribut eines anderen
- **Modul / Paket** – `.py`-Datei / Ordner mit `__init__.py`
- **`@dataclass`** – erzeugt `__init__`, `__repr__`, `__eq__` (Wertevergleich)
- **Vererbung, Ober-/Unterklasse** – „ist ein“, `class Unter(Ober):`
- **`super()`** – Zugriff auf die Oberklasse: `super().__init__(…)`, `super().methode()`
- **Überschreiben (Overriding)** – gleiche Methode in der Unterklasse ersetzt die der Oberklasse
- **`@override`** – Markierung aus `typing`, ty prüft, ob wirklich etwas überschrieben wird
- **MRO** – Suchreihenfolge der Methoden (`Klasse.__mro__`), endet bei `object`
- **`isinstance` vs. `type(x) is`** – mit Oberklassen vs. nur genaue Klasse

### VL05 Übung 4: Produkte kapseln (`uebung4.py`, ca. 15 Min.)
Klasse `Produkt` aus Übung 2 übernehmen: (1) Bestand in `_bestand`, Property `bestand` **ohne** Setter;
`einlagern`/`verkaufen` arbeiten mit `self._bestand`. (2) Preis in `_preis`, Property `preis` **mit** Setter, der
negative Preise mit Meldung abweist; `__init__` nutzt den Setter. (3) Property `bruttopreis` mit
`MWST_SATZ: Final = Decimal("0.19")`, gerundet mit `.quantize(Decimal("0.01"))`. (4) `kaffee.preis = Decimal("-5")`
und `kaffee.bestand = 100` ausprobieren. Zusatz: `reduzierter_preis(prozent)`, außerhalb 0–90 Originalpreis.

*Lösungshinweise (laut Musterlösung):*

```python
MWST_SATZ: Final = Decimal("0.19")

class Produkt:
    def __init__(self, name: str, preis: Decimal, bestand: int) -> None:
        self.name = name
        self._preis = Decimal(0)
        self.preis = preis              # Setter!
        self._bestand = bestand

    @property
    def bestand(self) -> int:
        return self._bestand

    @property
    def preis(self) -> Decimal:
        return self._preis

    @preis.setter
    def preis(self, neuer_preis: Decimal) -> None:
        if neuer_preis < 0:
            print(f"Ungültiger Preis: {neuer_preis}")
            return
        self._preis = neuer_preis

    @property
    def bruttopreis(self) -> Decimal:
        return (self._preis * (1 + MWST_SATZ)).quantize(Decimal("0.01"))
```

- Kaffee (12.99, 40): `bruttopreis` → `15.46`; `kaffee.preis = Decimal("-5")` → `Ungültiger Preis: -5`, Preis bleibt
  `12.99`.
- `kaffee.bestand = 100` → ty `error[invalid-assignment]: Cannot assign to read-only property`, Laufzeit
  `AttributeError: property 'bestand' of 'Produkt' object has no setter` → Zeile danach wieder löschen.
- Zusatz: `(self._preis * (100 - prozent) / 100).quantize(...)` → 20 % = `10.39`, 95 % → `12.99`.

### VL05 Übung 5: Ein Warenkorb (`uebung5.py`, ca. 15 Min.)
(1) `@dataclass Kunde(name, email)`. (2) `@dataclass Position(produkt: Produkt, menge: int)` mit
`summe() -> Decimal`. (3) Klasse `Warenkorb` mit `self.kunde` und `self.positionen: list[Position] = []` in
`__init__`; `hinzufuegen(produkt, menge)` legt eine Position an, wenn der Bestand reicht, sonst Meldung.
(4) `gesamtsumme()` und `ausgeben()`. (5) Test mit zwei Produkten, auch zu großer Menge. Zusatz: auf
`produkt.py`, `warenkorb.py`, `uebung5.py` verteilen.

*Lösungshinweise:*

```python
@dataclass
class Position:
    produkt: Produkt
    menge: int

    def summe(self) -> Decimal:
        return self.produkt.preis * self.menge

class Warenkorb:
    def __init__(self, kunde: Kunde) -> None:
        self.kunde = kunde
        self.positionen: list[Position] = []     # in __init__ → pro Objekt eine neue Liste

    def hinzufuegen(self, produkt: Produkt, menge: int) -> None:
        if menge > produkt.bestand:
            print(f"Nur noch {produkt.bestand} x {produkt.name} auf Lager.")
            return
        self.positionen.append(Position(produkt, menge))

    def gesamtsumme(self) -> Decimal:
        summe = Decimal(0)
        for position in self.positionen:
            summe += position.summe()
        return summe
```

- Test der Lösung: 2 × Kaffee (12.99) = `25.98`, 3 × Grüner Tee (3.49) = `10.47`, 50 × Kaffee → `Nur noch 40 x
  Kaffee 1 kg auf Lager.`, Summe `36.45` (nachgerechnet).
- `anna == Kunde("Anna Berger", "anna.berger@example.com")` → `True` dank `@dataclass`.
- Wichtig für VL07: Diese `Kunde`/`Position`/`Warenkorb` werden im Projekt „Kaffeeshop“ wiederverwendet.

### VL06 Übung 2: Mitarbeiter arbeiten unterschiedlich (`uebung2.py`, ca. 15 Min.)
(1) `Mitarbeiter.arbeiten() -> str` → `"Lena arbeitet."`. (2) Mit `@override` überschreiben: Entwickler →
`"Lena schreibt Code in Python."`, Manager → `"Tom leitet ein Team mit 6 Personen."`. (3) `monatskosten() -> int`
liefert das Gehalt; Manager zusätzlich 150 Euro Führungszulage je Teammitglied über `super().monatskosten()`.
(4) `Entwickler.__str__` ergänzt die Oberklassen-Ausgabe → `Lena: 4200 Euro im Monat, Python`. (5) `@override`
über `def arbeitn` – was meldet ty? Zusatz: `Manager.__mro__` ausgeben und erklären.

*Lösungshinweise:*

```python
from typing import Final, override

FUEHRUNGSZULAGE: Final = 150

class Manager(Mitarbeiter):
    ...
    @override
    def monatskosten(self) -> int:
        return super().monatskosten() + FUEHRUNGSZULAGE * self.teamgroesse

class Entwickler(Mitarbeiter):
    ...
    @override
    def __str__(self) -> str:
        return f"{super().__str__()}, {self.programmiersprache}"
```

- Tom: `5800 + 150 * 6 = 6700`; Lena: `4200`.
- `@override` über `arbeitn` → ty `invalid-explicit-override` („does not override anything“).
- Zusatz: `Manager.__mro__` → `Manager, Mitarbeiter, object`; `arbeiten`/`monatskosten` findet Python in `Manager`,
  `__str__` erst in `Mitarbeiter`.

## Typische Fehler / Fallen

- **Setter im `__init__` umgehen** (`self._preis = preis`) → Regel gilt beim Anlegen nicht.
- **Property mit Klammern** (`kaffee.bruttopreis()`) → `TypeError: 'decimal.Decimal' object is not callable`.
- **Getter und Setter mit verschiedenen Namen** – der Setter muss `@preis.setter` heißen **und** `def preis` sein.
- **Leere Liste als Parameter-Standardwert** statt in `__init__` → von allen Objekten geteilt (VL04).
- **`@dataclass` erzeugt keine Prüfungen** und keine Properties – nur `__init__`, `__repr__`, `__eq__`.
- **`super().__init__(…)` vergessen** → `AttributeError` erst später; ty schweigt.
- **Vererbung für „hat ein“** (Warenkorb erbt von Kunde) – falsch, Attribut nehmen.
- **Tippfehler beim Überschreiben** → still neue Methode; `@override` macht es sichtbar.
- **Überladen mit Überschreiben verwechseln** – Klausurklassiker.
