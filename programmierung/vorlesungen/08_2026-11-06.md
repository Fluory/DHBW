### Vormittag, Teil 1: Polymorphie (VL06 Folien 30–40)

Einstiegsfrage: *„Sie klicken im Onlineshop auf ‚Jetzt bezahlen‘. Was muss der Shop je nach Zahlungsart tun?“*

**Was ist das?** Polymorphie („Vielgestaltigkeit“) heißt: **dieselbe Zeile Code** macht je nach Objekt **etwas
anderes**. Die Kasse ruft immer `zahlungsart.bezahlen(betrag)` auf – bei einer Kreditkarte wird abgebucht, beim
Rechnungskauf eine Rechnung geschrieben. Die Kasse muss die Zahlungsarten nicht auseinanderhalten.

Das ist nichts Neues, sondern **Überschreiben (Termin 7) + eine Liste/Funktion, die nur die Oberklasse kennt**.

```python
from decimal import Decimal
from typing import override


class Zahlungsart:
    def bezahlen(self, betrag: Decimal) -> str:
        return f"{betrag} Euro bezahlt"


class Kreditkarte(Zahlungsart):
    def __init__(self, nummer: str) -> None:
        self.nummer = nummer

    @override
    def bezahlen(self, betrag: Decimal) -> str:
        return f"{betrag} Euro von Karte ...{self.nummer[-4:]} abgebucht"


class Rechnungskauf(Zahlungsart):
    @override
    def bezahlen(self, betrag: Decimal) -> str:
        return f"Rechnung über {betrag} Euro, zahlbar in 14 Tagen"


class Lastschrift(Zahlungsart):          # später neu dazugekommen
    def __init__(self, iban: str) -> None:
        self.iban = iban

    @override
    def bezahlen(self, betrag: Decimal) -> str:
        return f"{betrag} Euro von IBAN ...{self.iban[-4:]} eingezogen"


def kasse(zahlungsart: Zahlungsart, betrag: Decimal) -> None:
    print(zahlungsart.bezahlen(betrag))  # immer dieselbe Zeile


kasse(Kreditkarte("4111111111111234"), Decimal("49.90"))
kasse(Rechnungskauf(), Decimal("199.00"))
kasse(Lastschrift("DE89370400440532013000"), Decimal("20.00"))
```

Ausgabe:

```
49.90 Euro von Karte ...1234 abgebucht
Rechnung über 199.00 Euro, zahlbar in 14 Tagen
20.00 Euro von IBAN ...3000 eingezogen
```

**Schritt für Schritt – was passiert bei `zahlungsart.bezahlen(betrag)`?**

| Aufruf | `zahlungsart` zeigt auf | Python sucht `bezahlen` … | Ergebnis |
|---|---|---|---|
| 1 | Kreditkarte-Objekt | in `Kreditkarte` → gefunden | „… von Karte ...1234 abgebucht“ |
| 2 | Rechnungskauf-Objekt | in `Rechnungskauf` → gefunden | „Rechnung über 199.00 Euro …“ |
| 3 | Lastschrift-Objekt | in `Lastschrift` → gefunden | „… von IBAN ...3000 eingezogen“ |

**Nutzen (Folie 35):** Für die Lastschrift kam nur eine **neue Klasse** dazu – `kasse()` blieb **unverändert**.

**Typangabe vs. Objekt – wer entscheidet was? (Folie 34)**

- Die **Typangabe** `zahlungsart: Zahlungsart` entscheidet, was **ty erlaubt**: nur das, was *jede* Zahlungsart
  hat. `zahlungsart.bezahlen(…)` ist ok; `zahlungsart.nummer` → ty-Fehler `unresolved-attribute` (ein
  Rechnungskauf hat keine Nummer).
- Das **Objekt** entscheidet beim Ausführen, **welches** `bezahlen()` läuft.
- Braucht man doch die Nummer: vorher `if isinstance(zahlungsart, Kreditkarte):` – danach erlaubt ty
  `zahlungsart.nummer`. Einen Cast wie in Java braucht Python nicht.

**Duck Typing (Folie 39):** Python prüft beim Ausführen nur, **ob die Methode da ist** („Wenn es quakt wie eine
Ente …“). Ein `Gutschein`, der **nicht** von `Zahlungsart` erbt, aber `bezahlen()` hat, läuft:
`15.00 Euro mit Gutschein bezahlt`. **ty** meldet aber ``error[invalid-argument-type]: Argument to function `kasse`
is incorrect``. Deshalb in der Vorlesung: **immer erben**, dann prüft ty mit.

### Vormittag, Teil 2: `object`, `__repr__` und abstrakte Klassen (Folien 42–47)

**`object` ist die Wurzel jeder Klasse.** Auch `class Leer: pass` erbt von `object` (`Leer.__bases__` →
`(<class 'object'>,)`). Von dort kommen schlichte Standardversionen: `print(Leer())` →
`<__main__.Leer object at 0x…>`, `Leer() == Leer()` → `False` (vergleicht nur, ob es *dasselbe* Objekt ist). Dein
`__str__` aus VL05 hat also schon eine Methode von `object` **überschrieben**.

**`__repr__`** = Beschreibung für Entwickler, Format wie bei `@dataclass`: `Klasse(attribut=wert, …)`.

```python
from typing import override


class Konto:
    def __init__(self, inhaber: str, kontostand: int) -> None:
        self.inhaber = inhaber
        self.kontostand = kontostand

    @override
    def __repr__(self) -> str:
        return f"{type(self).__name__}(inhaber={self.inhaber!r}, kontostand={self.kontostand})"


class Sparkonto(Konto):
    pass


print(Konto("Anna", 1000))    # Konto(inhaber='Anna', kontostand=1000)
print(Sparkonto("Ben", 50))   # Sparkonto(inhaber='Ben', kontostand=50)
```

- `type(self).__name__` = Name der **tatsächlichen** Klasse → passt automatisch für Unterklassen.
- `!r` setzt Texte in Anführungszeichen (`'Anna'`), Zahlen bleiben ohne.
- Gibt es kein `__str__`, nimmt `print()` das `__repr__`.

**Abstrakte Klassen – was ist das?** Frage in die Runde: *„Was soll `Zahlungsart().bezahlen(…)` eigentlich tun?“* –
Nichts Sinnvolles: Eine „Zahlungsart an sich“ gibt es nicht. Eine **abstrakte Klasse** ist wie ein **Formular mit
Pflichtfeldern**: Sie legt fest, *welche* Methoden jede Unterklasse haben **muss**, aber nicht *wie*. Objekte kann
man von ihr **nicht** erzeugen. Zwei Zutaten, **beide** nötig: erben von `ABC` **und** `@abstractmethod`.

```python
from abc import ABC, abstractmethod
from decimal import Decimal
from typing import override


class Zahlungsart(ABC):                        # 1. Zutat: erbt von ABC
    @abstractmethod                            # 2. Zutat: Pflichtmethode
    def bezahlen(self, betrag: Decimal) -> str:
        """Jede konkrete Zahlungsart muss das umsetzen."""

    def beleg(self, betrag: Decimal) -> str:   # konkrete Methode, für alle gleich
        return f"Beleg: {self.bezahlen(betrag)}"


class Rechnungskauf(Zahlungsart):
    @override
    def bezahlen(self, betrag: Decimal) -> str:
        return f"Rechnung über {betrag} Euro, zahlbar in 14 Tagen"


class PayPal(Zahlungsart):                     # bezahlen vergessen!
    def __init__(self, email: str) -> None:
        self.email = email


print(Rechnungskauf().beleg(Decimal("80.00")))
# Beleg: Rechnung über 80.00 Euro, zahlbar in 14 Tagen
Zahlungsart()
# TypeError: Can't instantiate abstract class Zahlungsart without an implementation for abstract method 'bezahlen'
PayPal("anna@example.com")
# TypeError: Can't instantiate abstract class PayPal without an implementation for abstract method 'bezahlen'
```

- Der Fehler kommt beim **Erzeugen** des Objekts, nicht erst beim Aufruf von `bezahlen`.
- ty meldet ihn schon **vor dem Start**: `call-non-callable: Cannot instantiate abstract class`.
- Eine Unterklasse, die **nicht alle** abstrakten Methoden umsetzt, bleibt selbst abstrakt (PayPal).
- Abstrakt und konkret dürfen gemischt werden: `beleg()` ruft das jeweilige `bezahlen()` auf (wieder Polymorphie).
- Java: `abstract class … extends`; Python: `class X(ABC)` + `@abstractmethod` aus dem Modul `abc`.

### Vormittag, Teil 3: Fähigkeiten statt Interfaces (Folien 49–57)

**Was ist das?** Rechnung, Lieferschein, Newsletter *sind* Dokumente – das ist eine **Kategorie** (Oberklasse).
„Kann gedruckt werden“ / „kann per E-Mail versendet werden“ sind **Fähigkeiten**, die quer durch die Klassen gehen.
Java nimmt dafür `interface` + `implements`. Python hat kein `interface`: Eine Fähigkeit ist eine **abstrakte Klasse
mit nur abstrakten Methoden** (keine Attribute, kein `__init__`). Python erlaubt **mehrere Oberklassen** – die
Fähigkeiten stehen einfach mit in der Klammer, **Kategorie zuerst**.

```python
from abc import ABC, abstractmethod
from typing import override


class Druckbar(ABC):
    @abstractmethod
    def drucken(self) -> None: ...


class Versendbar(ABC):
    @abstractmethod
    def versenden(self, email: str) -> None: ...


class Dokument:                                  # Kategorie: Attribut + Konstruktor
    def __init__(self, nummer: str) -> None:
        self.nummer = nummer


class Rechnung(Dokument, Druckbar, Versendbar):  # kann beides
    @override
    def drucken(self) -> None:
        print(f"Rechnung {self.nummer} wird gedruckt")

    @override
    def versenden(self, email: str) -> None:
        print(f"Rechnung {self.nummer} geht an {email}")


class Lieferschein(Dokument, Druckbar):          # kann nur drucken
    @override
    def drucken(self) -> None:
        print(f"Lieferschein {self.nummer} wird gedruckt")


class Newsletter(Dokument, Versendbar):          # kann nur versenden
    @override
    def versenden(self, email: str) -> None:
        print(f"Newsletter {self.nummer} geht an {email}")


ablage: list[Dokument] = [Rechnung("R-1001"), Lieferschein("L-2001"), Newsletter("N-11")]
for dokument in ablage:
    if isinstance(dokument, Druckbar):
        dokument.drucken()
    if isinstance(dokument, Versendbar):
        dokument.versenden("einkauf@kunde.de")
```

**Rundentabelle** – die Schleife nimmt nacheinander jedes Element der Liste in `dokument`:

| Runde | `dokument` | `Druckbar`? | `Versendbar`? | Ausgabe |
|---|---|---|---|---|
| 1 | Rechnung R-1001 | ja | ja | „Rechnung R-1001 wird gedruckt“, „Rechnung R-1001 geht an einkauf@kunde.de“ |
| 2 | Lieferschein L-2001 | ja | nein | „Lieferschein L-2001 wird gedruckt“ |
| 3 | Newsletter N-11 | nein | ja | „Newsletter N-11 geht an einkauf@kunde.de“ |

Ohne die `isinstance`-Prüfung gäbe es in Runde 2 einen `AttributeError` (Lieferschein hat kein `versenden`).

**Abstrakte Klasse oder Fähigkeit? (Folie 56)**

- **Abstrakte Klasse (Kategorie):** „ist ein …“; konkrete **und** abstrakte Methoden; Attribute und `__init__`
  erlaubt; **eine** pro Klasse; Java `abstract class`/`extends`.
- **Fähigkeit (Interface):** „kann …“; **nur** abstrakte Methoden; keine Attribute; **beliebig viele**; Java
  `interface`/`implements`.
- Gemeinsam: beide erben von `ABC`, von beiden gibt es **keine Objekte**.
- Ausblick: `typing.Protocol` – erfüllt schon, wer die Methoden hat, ohne zu erben (Duck Typing, das ty prüft).

## Wichtige Begriffe

- **Polymorphie** – derselbe Methodenaufruf, unterschiedliches Verhalten je nach Klasse des Objekts
- **Typangabe vs. Objekt** – Typangabe: was ty erlaubt; Objekt: welche Methode beim Ausführen läuft
- **Duck Typing** – Python prüft nur, ob die Methode existiert; ty prüft trotzdem die Typangabe
- **`object`** – Wurzel jeder Klasse; Standard-`__str__`, `__repr__`, `__eq__`
- **`__repr__`** – Entwickler-Darstellung `Klasse(attr=wert)`; `type(self).__name__`, `!r`
- **Abstrakte Klasse** – erbt von `ABC`, hat `@abstractmethod`; keine Objekte möglich
- **Konkrete Klasse** – setzt alle abstrakten Methoden um, Objekte möglich
- **Fähigkeit (Interface)** – abstrakte Klasse nur mit abstrakten Methoden, „kann …“; mehrere pro Klasse
- **Mehrfachvererbung** – `class Laptop(Geraet, Aufladbar, Netzwerkfaehig)`; in der VL nur für Fähigkeiten
- **Pair Programming** – zu zweit an einem Rechner, Rollen regelmäßig tauschen
- **`Produkt | None`** – Rückgabetyp „ein Produkt oder nichts“ (bei `finden`)

### VL06 Übung 3: Personalkosten für das ganze Team (`uebung3.py`, ca. 15 Min.)
(1) Klassen aus Übung 2 übernehmen, `team: list[Mitarbeiter]` mit sechs Personen (gemischt). (2) In einer Schleife
für jede Person `arbeiten()` ausgeben. (3) `personalkosten(team: list[Mitarbeiter]) -> int` addiert die
Monatskosten. (4) Neue Unterklasse `Werkstudent` (+ `stunden_pro_woche`), `arbeiten()` → `"Jonas arbeitet 20 Stunden
pro Woche mit."`; zwei Werkstudenten aufnehmen – muss `personalkosten()` geändert werden? Zusatz: `Freelancer`, der
**nicht** erbt, aber `arbeiten()` und `monatskosten()` hat – läuft das? Was meldet ty?

*Lösungsskizze* (Klassen `Mitarbeiter`, `Entwickler`, `Manager` wie in [Termin 7](07_2026-11-03.md)):

```python
class Werkstudent(Mitarbeiter):
    def __init__(self, name: str, monatsgehalt: int, stunden_pro_woche: int) -> None:
        super().__init__(name, monatsgehalt)
        self.stunden_pro_woche = stunden_pro_woche

    @override
    def arbeiten(self) -> str:
        return f"{self.name} arbeitet {self.stunden_pro_woche} Stunden pro Woche mit."


def personalkosten(team: list[Mitarbeiter]) -> int:
    summe = 0                          # Startwert VOR der Schleife
    for person in team:
        summe += person.monatskosten() # Polymorphie: jede Person rechnet selbst
    return summe                       # NACH der Schleife (nicht eingerückt!)


team: list[Mitarbeiter] = [
    Entwickler("Lena", 4200, "Python"),
    Entwickler("Ali", 4400, "Java"),
    Manager("Tom", 5800, 6),
    Mitarbeiter("Sara", 3600),
    Mitarbeiter("Max", 3400),
    Manager("Eva", 6100, 3),
]
for person in team:
    print(person.arbeiten())
print(f"Personalkosten: {personalkosten(team)} Euro")   # Personalkosten: 28850 Euro
```

**Rundentabelle für `personalkosten(team)`:**

| Runde | `person` | `person.monatskosten()` | `summe` danach |
|---|---|---|---|
| Start | – | – | 0 |
| 1 | Lena (Entwickler) | 4200 (geerbt) | 4200 |
| 2 | Ali (Entwickler) | 4400 | 8600 |
| 3 | Tom (Manager, 6) | 5800 + 150 · 6 = 6700 | 15300 |
| 4 | Sara | 3600 | 18900 |
| 5 | Max | 3400 | 22300 |
| 6 | Eva (Manager, 3) | 6100 + 150 · 3 = 6550 | 28850 |

- Ausgabe der ersten Schleife: `Lena schreibt Code in Python.`, `Ali schreibt Code in Java.`, `Tom leitet ein Team
  mit 6 Personen.`, `Sara arbeitet.`, `Max arbeitet.`, `Eva leitet ein Team mit 3 Personen.`
- (4) Mit `Werkstudent("Jonas", 1300, 20)` und `Werkstudent("Mia", 1100, 16)`: `28850 + 1300 + 1100 = 31250`.
  **`personalkosten()` bleibt unverändert** – genau das ist der Nutzen der Polymorphie.
- Zusatz: Der `Freelancer` **läuft** (Duck Typing, mit Honorar 5000 → 36250 Euro), aber ty meldet bei
  `team.append(Freelancer(…))` `invalid-argument-type`, weil er kein `Mitarbeiter` ist.

### VL06 Übung 4: Geräteverwaltung, Teil 1 (`uebung4.py`, ca. 20 Min.)
(1) Abstrakte Klasse `Geraet` mit `hersteller`, `modell`, `baujahr: int`, konkreter Methode `einschalten()`
(`Lenovo ThinkPad T14 wird eingeschaltet.`) und abstrakter Methode `status() -> str`. (2) `__repr__` im
vereinbarten Format. (3) Unterklassen `Laptop`, `Smartphone` (`akku_prozent`) und `Router` (`verbundene_geraete`),
jede mit eigenem `status()`. (4) `inventar: list[Geraet]` mit drei Geräten; jedes mit Status ausgeben und
einschalten. (5) `Geraet(…)` direkt erzeugen – was melden ty und Python? Zusatz: eigene Methoden wie `screenshot()`
(Smartphone) oder `firmware_update()` (Router) in der Schleife aufrufen – was braucht man dafür?

*Lösungsskizze:*

```python
from abc import ABC, abstractmethod
from typing import override


class Geraet(ABC):
    def __init__(self, hersteller: str, modell: str, baujahr: int) -> None:
        self.hersteller = hersteller
        self.modell = modell
        self.baujahr = baujahr

    def einschalten(self) -> None:
        print(f"{self.hersteller} {self.modell} wird eingeschaltet.")

    @abstractmethod
    def status(self) -> str:
        """Jedes Gerät beschreibt seinen Zustand selbst."""

    @override
    def __repr__(self) -> str:
        return (
            f"{type(self).__name__}(hersteller={self.hersteller!r}, "
            f"modell={self.modell!r}, baujahr={self.baujahr})"
        )


class Laptop(Geraet):
    def __init__(self, hersteller: str, modell: str, baujahr: int, akku_prozent: int) -> None:
        super().__init__(hersteller, modell, baujahr)
        self.akku_prozent = akku_prozent

    @override
    def status(self) -> str:
        return f"Akku {self.akku_prozent} %"

# Smartphone genauso wie Laptop; Router mit verbundene_geraete → f"{…} Geräte verbunden"

for geraet in inventar:
    print(geraet, "-", geraet.status())
    geraet.einschalten()
```

**Rundentabelle** (Inventar: Lenovo-Laptop 80 %, Samsung Galaxy S24 35 %, AVM-Router 12 Geräte):

| Runde | `geraet` | `print(geraet, "-", geraet.status())` | `einschalten()` |
|---|---|---|---|
| 1 | Laptop | `Laptop(hersteller='Lenovo', modell='ThinkPad T14', baujahr=2023) - Akku 80 %` | `Lenovo ThinkPad T14 wird eingeschaltet.` |
| 2 | Smartphone | `Smartphone(hersteller='Samsung', modell='Galaxy S24', baujahr=2024) - Akku 35 %` | `Samsung Galaxy S24 wird eingeschaltet.` |
| 3 | Router | `Router(hersteller='AVM', modell='FRITZ!Box 7590', baujahr=2021) - 12 Geräte verbunden` | `AVM FRITZ!Box 7590 wird eingeschaltet.` |

- `__repr__` steht nur **einmal** in `Geraet` – dank `type(self).__name__` steht trotzdem „Laptop“, „Router“ da.
- (5) ty: ``call-non-callable: Cannot instantiate abstract class `Geraet` ``; Python: `TypeError: Can't instantiate

```python
# lager.py
class Lager:
    def __init__(self, produkte: list[Produkt]) -> None:
        self.produkte = produkte

    def anzeigen(self) -> None:
        for produkt in self.produkte:
            print(produkt)

    def finden(self, nummer: int) -> Produkt | None:
        for produkt in self.produkte:
            if produkt.nummer == nummer:
                return produkt         # gefunden → sofort raus aus der Methode
        return None                    # Schleife ganz durchgelaufen, nichts gefunden

    def suchen(self, text: str) -> list[Produkt]:
        treffer: list[Produkt] = []
        for produkt in self.produkte:
            if text.lower() in produkt.name.lower():
                treffer.append(produkt)
        return treffer
```

```python
# warenkorb.py
from dataclasses import dataclass
from decimal import Decimal

from produkt import Produkt


@dataclass
class Kunde:
    name: str
    email: str


@dataclass
class Position:
    produkt: Produkt
    menge: int

    def summe(self) -> Decimal:
        return self.produkt.bruttopreis * self.menge


class Warenkorb:
    def __init__(self, kunde: Kunde) -> None:
        self.kunde = kunde
        self.positionen: list[Position] = []

    def _position_zu(self, nummer: int) -> Position | None:   # Hilfsmethode, wie finden()
        for position in self.positionen:
            if position.produkt.nummer == nummer:
                return position
        return None

    def hinzufuegen(self, produkt: Produkt, menge: int) -> bool:
        vorhanden = self._position_zu(produkt.nummer)
        schon_im_korb = 0 if vorhanden is None else vorhanden.menge
        if schon_im_korb + menge > produkt.bestand:
            return False                                     # main.py gibt die Meldung aus
        if vorhanden is None:
            self.positionen.append(Position(produkt, menge)) # neue Position
        else:
            vorhanden.menge += menge                         # vorhandene erhöhen
        return True

    def entfernen(self, nummer: int) -> bool:
        position = self._position_zu(nummer)
        if position is None:
            return False
        self.positionen.remove(position)
        return True

    def gesamtsumme(self) -> Decimal:
        summe = Decimal(0)
        for position in self.positionen:
            summe += position.summe()
        return summe

    def ist_leer(self) -> bool:
        return len(self.positionen) == 0

    def anzeigen(self) -> None:
        print(f"Warenkorb von {self.kunde.name}")
        for position in self.positionen:
            print(f"{position.menge} x {position.produkt.name}: {position.summe()} Euro")
        print(f"Summe: {self.gesamtsumme()} Euro")
```

**Schritt für Schritt: „erst 3, dann noch 1 French Press“** (Bestand 3, Folie 13):

| `hinzufuegen(fp, 5)`, Korb leer | `None` | 0 | 0 + 5 > 3 → ja | `False` |
| `hinzufuegen(fp, 3)` | `None` | 0 | 0 + 3 > 3 → nein | neue Position (3), `True` |
| `hinzufuegen(fp, 1)` | Position French Press | 3 | 3 + 1 > 3 → ja | `False`, abgelehnt |

### Die wichtigsten Code-Ideen (eigenes Beispiel)

Ein kleines eigenes Programm im gleichen Stil, das die Kernpunkte von VL02, VL04 und VL06 zeigt
(mit `python3 -I` ausgeführt, Python 3.13):

```python
from abc import ABC, abstractmethod
from decimal import Decimal


class Tarif(ABC):
    def __init__(self, name: str) -> None:
        self.name = name
        self.besuche: list[int] = []  # Minuten je Besuch

    @abstractmethod
    def monatsbeitrag(self) -> Decimal: ...

    def einchecken(self, minuten: int) -> None:
        self.besuche.append(minuten)


class Basic(Tarif):
    def monatsbeitrag(self) -> Decimal:
        return Decimal("24.90")


class Student(Basic):
    def monatsbeitrag(self) -> Decimal:
        return super().monatsbeitrag() - Decimal("5.00")


def gewicht(woche: int) -> float:
    if woche == 1:          # Basisfall
        return 40.0
    return gewicht(woche - 1) + 2.5


mia = Student("Mia")
for minuten in [50, 70, 40]:
    mia.einchecken(minuten)
print(mia.name, mia.monatsbeitrag(), len(mia.besuche), sum(mia.besuche))
print(gewicht(3))
print(0.1 + 0.2, Decimal("0.1") + Decimal("0.2"))
print(130 // 60, 130 % 60)
```

Ausgabe:

```text
Mia 19.90 3 160
45.0
0.30000000000000004 0.3
2 10
```

- `Student` erbt von `Basic`, `super().monatsbeitrag()` holt den Basic-Preis → 19.90.
- `gewicht(3)` ruft `gewicht(2)` und `gewicht(1)` auf: 40 + 2,5 + 2,5 = 45.0.
- `float` rechnet ungenau (0.30000000000000004), `Decimal` mit Text-Argument genau → darum Geld als `Decimal`.
- `Tarif("Max")` geht nicht: `TypeError: Can't instantiate abstract class Tarif …` – schon beim **Erzeugen**.
- `gewicht(0)` erreicht den Basisfall nie (0, −1, −2 …) → `RecursionError`. Die Antwort auf die offene Frage von
  Folie 10: Ein sicherer Basisfall wäre `if woche <= 1:`.

## Typische Fehler / Fallen

- **Unterklassen-Attribut über die Oberklassen-Typangabe** (`zahlungsart.nummer`) → ty `unresolved-attribute`;
  erst `isinstance` prüfen.
- **Duck Typing heißt nicht „ty ist egal“:** Programm läuft, ty meldet `invalid-argument-type`.
- **Nur eine Zutat für abstrakt:** `class Geraet:` mit `@abstractmethod`, aber ohne `(ABC)` → Python verhindert das
  Erzeugen **nicht**. Es braucht `(ABC)` **und** `@abstractmethod`.
- **Fehler „erst beim Aufruf“ erwarten** – der `TypeError` kommt schon beim **Erzeugen** (`Geraet(…)`).
- **`isinstance` vergessen** vor einer Fähigkeits-Methode → `AttributeError`.
- **`__repr__` mit festem Namen** (`"Geraet(…)"`) statt `type(self).__name__`.
- **Fähigkeit mit `__init__`/Attributen** – laut Vorlesung nur abstrakte Methoden.
- **Schleifen:** `summe = 0` **in** die Schleife geschrieben (wird jede Runde zurückgesetzt); `return` **in** der
  Schleife statt danach (bricht nach Runde 1 ab).
- **Kaffeeshop:** schon im Korb liegende Menge nicht mitzählen; zweite Position statt Menge erhöhen;
  `korb.positionen.clear()` leert in Stufe 2 auch die Liste der Bestellung (zwei Namen, eine Liste) →
  `korb.positionen = []`.
