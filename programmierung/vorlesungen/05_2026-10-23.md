## Vormittag: VL05 – Objektorientierte Programmierung I

Agenda: Klassen und Objekte → Methoden und `self` → Namen, Objekte und Klassenattribute → Kapselung mit
Properties → zusammengesetzte Klassen und `@dataclass` (nach jedem Block eine Übung).

### Klassen und Objekte
**OOP** = Programme bestehen aus **Objekten**, die zusammenarbeiten. Ein Objekt

- hat **Attribute** (Daten → sein **Zustand**),
- hat **Methoden** (Funktionen → sein **Verhalten**, können den Zustand ändern),
- gehört zu einer **Klasse** = dem **Bauplan**. Ein Objekt heißt auch **Instanz** der Klasse.

Aus einer Klasse lassen sich beliebig viele Objekte bauen. Jedes Objekt hat **eigene Werte** für die Attribute; die
**Methoden stehen nur einmal in der Klasse** und gelten für alle Objekte. Darstellung als **UML-Klassendiagramm**:
oben Name, Mitte Attribute, unten Methoden (z. B. `Konto` | `inhaber`, `kontostand` | `einzahlen()`, `abheben()`).

Wir benutzen längst Objekte: `type(42)` → `<class 'int'>`, `"hallo".upper()` ist eine Methode von `str`,
`noten.append(3)` ändert den Zustand eines `list`-Objekts. `str(42)` und `list()` rufen Klassen auf und erzeugen
damit Objekte – genauso entstehen gleich eigene Objekte.

```python
class Konto:                                    # Klassenname in PascalCase
    def __init__(self, inhaber: str, kontostand: int) -> None:
        self.inhaber = inhaber                  # Attribut links, Parameter rechts
        self.kontostand = kontostand

anna = Konto("Anna", 100)                       # Objekt erzeugen: kein `new` wie in Java
ben = Konto("Ben", 250)
ben.kontostand = 300                            # ändert nur das Objekt, auf das ben zeigt
print(anna.inhaber, anna.kontostand)            # Anna 100
print(ben.inhaber, ben.kontostand)              # Ben 300
```

**Konstruktor `__init__` und `self`:**

- `__init__` läuft **automatisch** beim Erzeugen und setzt den Anfangszustand.
- Ablauf von `Konto("Anna", 100)`: Python legt ein **leeres Objekt** an, ruft `Konto.__init__` auf, `self` zeigt auf
  das neue Objekt; `self.inhaber = …` und `self.kontostand = …` legen die Attribute an. Der Rahmen von `__init__`
  verschwindet, das Objekt bleibt, und `anna` zeigt darauf.
- `self` ist **der erste Parameter**; Python übergibt ihn selbst, beim Aufruf schreibt man nur `Konto("Anna", 100)`.
- **Anders als Java:** Attribute werden **nicht vorab im Klassenrumpf deklariert**, sie entstehen in `__init__`;
  der Typ ergibt sich aus dem annotierten Parameter.
- **Genau ein `__init__`**, keine Überladung. Varianten über Standardwerte (VL04): mit `kontostand: int = 0` gehen
  `Konto("Anna", 100)` und `Konto("Ben")`.
- `__init__` gibt nichts zurück (`-> None`); das neue Objekt liefert der Aufruf `Konto(…)`.
- Ohne `__init__` erzeugt `Konto()` ein Objekt ohne Attribute.
- Namen mit doppelten Unterstrichen (`__init__`, `__str__` …) haben feste Bedeutung: **Dunder-Methoden**
  („double underscore“).

### Methoden und `self`
```python
class Konto:
    def __init__(self, inhaber: str, kontostand: int = 0) -> None:
        self.inhaber = inhaber
        self.kontostand = kontostand

    def einzahlen(self, betrag: int) -> None:
        self.kontostand += betrag

    def abheben(self, betrag: int) -> bool:
        if betrag > self.kontostand:            # Regel steht an EINER Stelle in der Klasse
            print("Abgelehnt: Der Kontostand reicht nicht.")
            return False
        self.kontostand -= betrag
        return True

anna = Konto("Anna", 100)
anna.einzahlen(50)
print(anna.abheben(500), anna.abheben(30), anna.kontostand)
# Abgelehnt: Der Kontostand reicht nicht.
# False True 120
```

- Eine **Methode** ist eine Funktion in der Klasse, erster Parameter `self`. Über `self.` liest/ändert sie die
  Attribute **ihres** Objekts.
- **Woher kommt `self`?** `anna.einzahlen(50)` ist dasselbe wie `Konto.einzahlen(anna, 50)`: Python sucht die
  Methode in der Klasse von `anna` und übergibt das **Objekt vor dem Punkt** als erstes Argument. Darum hat
  `einzahlen` zwei Parameter, beim Aufruf steht aber nur ein Argument. `self` entspricht `this` in Java, steht in
  Python aber ausdrücklich in jeder Methode; Attribute immer mit `self.` davor.
- Bei `ben.einzahlen(20)` zeigt `self` auf Bens Objekt – dieselbe Methode, anderes `self`.
- Namen: Klassen in **PascalCase** (`Konto`, `Lagerartikel`), Methoden und Attribute in **snake_case**.

**Objekte ausgeben – `__str__` und `__repr__`:**

```python
    def __str__(self) -> str:                   # für Menschen: print(konto)
        return f"Konto von {self.inhaber}: {self.kontostand} Euro"

    def __repr__(self) -> str:                  # für Entwickler: REPL, Listen
        return f"Konto({self.inhaber!r}, {self.kontostand})"

print(anna)                  # Konto von Anna: 120 Euro
print([anna, Konto("Ben")])  # [Konto('Anna', 120), Konto('Ben', 0)]
```

`__str__` entspricht `toString()` in Java. `__repr__` sieht möglichst aus wie der Aufruf, der das Objekt erzeugt;
`!r` setzt die Anführungszeichen. Ohne beide: `<konto.Konto object at 0x…>`. **Listen** zeigen ihre Elemente
immer mit `__repr__`, auch bei `print(liste)`.

### Namen, Objekte und Klassenattribute
- **Namen zeigen auf Objekte** (wie bei Listen in VL02–VL04): `konto2 = konto1` erzeugt **kein** zweites Konto,
  sondern ein zweites Namensschild. `konto2.einzahlen(50)` sieht man auch über `konto1`.
- **`is`** prüft Identität (dasselbe Objekt). **`==`** prüft bei eigenen Klassen **ohne `__eq__` ebenfalls nur die
  Identität** → zwei Konten mit gleichen Werten sind **nicht** `==`. (Mit `@dataclass` ändert sich das.)
- „Noch kein Objekt“ = `None` (Java: `null`), prüfen mit `if konto is None:`.

```python
konto1 = Konto("Anna", 100)
konto2 = konto1
konto2.einzahlen(50)
konto3 = Konto("Anna", 150)
print(konto1.kontostand)                     # 150
print(konto1 is konto2, konto1 == konto3)    # True False
```

**Attribute sind dynamisch – Tippfehler auch:** `anna.kontostnad = 500` legt zur Laufzeit **ohne Fehler** ein neues
Attribut an; `anna.kontostand` bleibt 100. `ty check` kennt die Attribute aus `__init__` und meldet
`error[unresolved-attribute]`. Deshalb **alle Attribute in `__init__` anlegen**, auch die, die anfangs leer sind
(`None`, `[]`).

**Klassenattribute** stehen direkt im Klassenrumpf; es gibt den Wert **nur einmal, in der Klasse** (Java: `static`).

```python
class Konto:
    anzahl_konten = 0                                   # Klassenattribut

    def __init__(self, inhaber: str, kontostand: int = 0) -> None:
        Konto.anzahl_konten += 1                        # immer über den Klassennamen ändern
        self.nummer = f"K{Konto.anzahl_konten:03}"      # Instanzattribut: K001, K002, …
        self.inhaber = inhaber
        self.kontostand = kontostand
```

**Falle:** **Lesen** über ein Objekt klappt (`ben.anzahl_konten` findet das Klassenattribut, solange das Objekt
keins mit diesem Namen hat). **Zuweisen** über ein Objekt (`ben.anzahl_konten += 1`) legt ein **neues
Instanzattribut** nur bei `ben` an: danach `ben.anzahl_konten == 3`, aber `Konto.anzahl_konten == 2` und
`anna.anzahl_konten == 2`. Gleiches gilt für `self.anzahl_konten += 1` in `__init__` – der Zähler bliebe stehen.

### Kapselung mit Properties
**Vier Grundprinzipien der OOP:** **Kapselung** (Daten und Methoden gehören zusammen, das Objekt bestimmt selbst,
wie sein Zustand geändert wird, und zeigt nach außen nur das Nötige), **Vererbung** („ist ein“), **Polymorphismus**
(verschiedene Klassen reagieren unterschiedlich auf denselben Aufruf), **Abstraktion** (Gemeinsamkeiten in einer
Oberklasse, Details weglassen). VL05 behandelt Kapselung, der Rest kommt in VL06/VL07.

Problem: Mit der einfachen Klasse kann jeder `anna.kontostand = -999` setzen. Kapselung: Die Klasse prüft selbst,
das Objekt bleibt immer gültig, das Innere lässt sich ändern, ohne dass anderer Code angepasst werden muss.

| Java | Python | Bedeutung |
|---|---|---|
| `public` | `kontostand` | Standard: alles ohne Unterstrich ist öffentlich |
| `private` / `protected` | `_kontostand` | **nur Konvention** „intern“; Python prüft nichts, `anna._kontostand` geht |
| package-private | – | gibt es nicht |

Zwei Unterstriche (`__kontostand`) → Python benennt um in `_Konto__kontostand` (**Name Mangling**): verhindert
Namenskonflikte bei Vererbung, **schützt den Wert aber nicht**.

**Getter/Setter wie in Java schreibt man in Python nicht** für jedes Attribut. Solange es nichts zu prüfen gibt,
bleibt das Attribut öffentlich. Gibt es Regeln, kommt eine **Property** dazu – eine Methode, die man **von außen
wie ein Attribut** benutzt (ohne Klammern):

```python
class Mitarbeiter:
    def __init__(self, name: str, monatsgehalt: int) -> None:
        self.name = name
        self.monatsgehalt = monatsgehalt

    @property
    def jahresgehalt(self) -> int:          # berechnet, bei jedem Zugriff neu
        return self.monatsgehalt * 12

lena = Mitarbeiter("Lena", 4200)
print(lena.jahresgehalt)   # 50400
lena.monatsgehalt = 4500
print(lena.jahresgehalt)   # 54000
# lena.jahresgehalt = 60000 → ty: Cannot assign to read-only property; Laufzeit: AttributeError
```

**Property mit Setter** – Wert liegt in `_kontostand`, `kontostand` ist die öffentliche Schnittstelle:

```python
class Konto:
    def __init__(self, inhaber: str, kontostand: Decimal) -> None:
        self.inhaber = inhaber
        self._kontostand = Decimal(0)
        self.kontostand = kontostand          # nutzt schon den Setter → Regel gilt beim Anlegen

    @property
    def kontostand(self) -> Decimal:          # Getter: anna.kontostand
        return self._kontostand

    @kontostand.setter
    def kontostand(self, neuer_wert: Decimal) -> None:   # Setter: anna.kontostand = x
        if neuer_wert < 0:
            print("Ungültig: negativer Kontostand.")
            return
        self._kontostand = neuer_wert
```
`anna.kontostand = Decimal("-500")` → Meldung, Wert bleibt `149.99`. Die Folie merkt selbst an: Üblich wäre bei
ungültigen Werten `raise ValueError(…)` statt `print`.

| Situation | in Python | Beispiel |
|---|---|---|
| Wert darf frei geändert werden | öffentliches Attribut | `self.inhaber` |
| nur lesen, Änderung über Methoden | `_attribut` + Property **ohne** Setter | Bestand |
| Änderung nur unter Regeln | `_attribut` + Property **mit** Setter | `kontostand` |
| Wert wird berechnet | Property ohne eigenes Attribut | `jahresgehalt` |

Vorteil: Man kann mit einem öffentlichen Attribut anfangen und **später** eine Property daraus machen – der
aufrufende Code bleibt gleich. Interne Hilfsmethoden ebenfalls mit Unterstrich: `_pruefe_betrag()`.

**Weitere Java-Modifikatoren:** `static`-Variable → Klassenattribut; `static final` → Modulkonstante
`MAX_KONTEN: Final = 100`; `static`-Methode → meist normale Modulfunktion (`@staticmethod` gibt es auch);
`final` → `@final` aus `typing` (prüft nur ty); `abstract` → `abc.ABC`/`@abstractmethod` (VL06).
`synchronized`, `transient`, `volatile`, `native` spielen keine Rolle.

### Zusammengesetzte Klassen und `@dataclass`
**Hat-ein-Beziehung (has-a, Komposition):** Objekte haben andere Objekte als Attribute – ein Konto **hat** einen
Kunden, eine Bestellung hat einen Kunden und mehrere Positionen. Jede Klasse bleibt klein, die Objekte arbeiten
zusammen, indem sie Methoden der anderen aufrufen.

```python
class Kunde:
    def __init__(self, name: str, ort: str) -> None:
        self.name = name
        self.ort = ort

class Konto:
    def __init__(self, kunde: Kunde, kontostand: int = 0) -> None:
        self.kunde = kunde                   # Konto HAT einen Kunden (Parametertyp = eigene Klasse)
        self.kontostand = kontostand

    def info(self) -> str:
        return f"{self.kunde.name}: {self.kontostand} Euro"

anna = Kunde("Anna Berger", "Heilbronn")
giro, spar = Konto(anna, 100), Konto(anna, 2500)
spar.info()                  # 'Anna Berger: 2500 Euro'
giro.kunde is spar.kunde     # True – beide zeigen auf dasselbe Kunden-Objekt
```

**Module und Pakete:** Jede `.py`-Datei ist ein **Modul**. Ein Ordner mit Modulen und einer (gern leeren)
`__init__.py` ist ein **Paket**; der Paketname ergibt sich aus dem Ordner (kein `package`-Kopf wie in Java).
`banking.konto` und `lager.konto` dürfen nebeneinander existieren. Import: `from banking.konto import Konto`.
Mehrere zusammengehörige Klassen dürfen in **einem** Modul stehen (keine Regel „eine öffentliche Klasse pro Datei“).

**`@dataclass`** erzeugt aus den **annotierten Attributen** automatisch `__init__`, `__repr__` und `__eq__`:

```python
from dataclasses import dataclass

@dataclass
class Kunde:
    name: str
    ort: str

k = Kunde("Anna Berger", "Heilbronn")
print(k)                                        # Kunde(name='Anna Berger', ort='Heilbronn')
print(k == Kunde("Anna Berger", "Heilbronn"))   # True  (Werte-Vergleich)
print(k is Kunde("Anna Berger", "Heilbronn"))   # False (trotzdem zwei Objekte)
```

| | `@dataclass` | normale Klasse |
|---|---|---|
| Zweck | vor allem Daten bündeln | Verhalten und Regeln im Vordergrund |
| Beispiele | `Kunde`, `Adresse`, `Bestellposition` | `Konto`, `Warenkorb`, `Lager` |
| `==` | vergleicht Werte | vergleicht Identität |

Auch Datenklassen dürfen Methoden und Properties haben; `@dataclass` spart nur Schreibarbeit.

**OOP Vor-/Nachteile:** + Struktur (Daten und Verhalten an einem Ort), Wiederverwendung, Kapselung, Abstraktion,
Erweiterbarkeit; − Einstieg braucht Übung, mehr Speicher/Laufzeit, für kleine Aufgaben oft umständlich,
Overengineering. Python zwingt zu keiner Klasse. **Geschichte:** Prozedurale Programmierung stößt in den 1980ern an
Grenzen; Simula (1967) und Smalltalk (1970er) legen das Fundament, C++ (1980er) bringt OOP in die Industrie,
Java (1995) verbreitet sie; Python (1991) ist von Anfang an objektorientiert – jeder Wert ist ein Objekt.

### Vererbung und `super()`
**Vererbung:** Eine Klasse übernimmt Attribute und Methoden einer anderen. **Oberklasse/Basisklasse** (allgemein)
→ **Unterklasse/abgeleitete Klasse** (speziell); die Unterklasse kann **ergänzen** und geerbte Methoden **ändern**.
Passt nur bei **„ist ein“** (Sparkonto ist ein Konto, Laptop ist ein Gerät). Für **„hat ein“** ist Vererbung das
falsche Werkzeug → Attribut (VL05). Nutzen: Gemeinsames an einer Stelle, kein doppelter Code (ein Fehler in
`einzahlen()` wird einmal behoben), Modelle wie in der Praxis, erweiterbar. Die Oberklasse weiß nichts von ihren
Unterklassen.

```python
class Sparkonto(Konto):                         # Oberklasse in Klammern = extends
    def __init__(self, inhaber: str, kontostand: int, zinssatz: int) -> None:
        super().__init__(inhaber, kontostand)   # Konto-Teil anlegen
        self.zinssatz = zinssatz                # neu: nur im Sparkonto

    def zinsen_gutschreiben(self) -> None:
        self.einzahlen(self.kontostand * self.zinssatz // 100)   # geerbte Methode

anna = Sparkonto("Anna", 1000, 2)
anna.einzahlen(500)              # geerbt
anna.zinsen_gutschreiben()       # 1500 * 2 // 100 = 30
print(anna)                      # Konto von Anna: 1530 Euro  (__str__ geerbt)
```

- `super().__init__(…)` ruft den Konstruktor der Oberklasse **mit demselben `self`** auf und legt `inhaber` und
  `kontostand` im Sparkonto-Objekt an; danach ergänzt die Unterklasse ihren Teil.
- **Falle: `super().__init__()` vergessen.** Hat die Unterklasse ein **eigenes** `__init__`, ruft Python das der
  Oberklasse **nicht von selbst** auf (Java ruft einen parameterlosen Oberklassen-Konstruktor automatisch). Das
  Objekt hat dann nur `zinssatz`; der Fehler zeigt sich erst bei der ersten Methode, die zugreift:
  `AttributeError: 'Sparkonto' object has no attribute 'kontostand'`. **ty meldet das nicht.**
- Hat die Unterklasse **kein** eigenes `__init__`, erbt sie das der Oberklasse – kein Aufruf nötig.
- **`isinstance(objekt, Klasse)`** prüft Klasse **und Oberklassen** (Java: `instanceof`):
  `isinstance(anna, Konto)` → `True`, aber `type(anna) is Konto` → `False` (nur genaue Klasse).
  `issubclass(Sparkonto, Konto)` → `True`.

| Zweck | Java | Python |
|---|---|---|
| erben | `class Sparkonto extends Konto` | `class Sparkonto(Konto):` |
| Konstruktor der Oberklasse | `super(inhaber, stand);` | `super().__init__(inhaber, stand)` |
| Methode der Oberklasse | `super.abheben(betrag)` | `super().abheben(betrag)` |
| Überschreiben markieren | `@Override` | `@override` aus `typing` |
| Klasse prüfen | `k instanceof Sparkonto` | `isinstance(k, Sparkonto)` |
| unvollständige Klasse | `abstract class` | `ABC` + `@abstractmethod` |
| mehrere Oberklassen | nicht möglich (dafür `interface`) | möglich |

### Methoden überschreiben
```python
from typing import override

class Girokonto(Konto):
    def __init__(self, inhaber: str, kontostand: int, dispo: int) -> None:
        super().__init__(inhaber, kontostand)
        self.dispo = dispo                       # so weit darf das Konto ins Minus

    @override
    def abheben(self, betrag: int) -> bool:      # gleicher Name, gleiche Parameter
        if betrag > self.kontostand + self.dispo:
            print("Abgelehnt: Der Dispo ist ausgeschöpft.")
            return False
        self.kontostand -= betrag
        return True

    @override
    def __str__(self) -> str:                    # ergänzen statt ersetzen
        return f"{super().__str__()} (Dispo {self.dispo} Euro)"

ben = Girokonto("Ben", 100, 500)
print(ben.abheben(400), ben.abheben(300), ben.kontostand)
# Abgelehnt: Der Dispo ist ausgeschöpft.
# True False -300
ben.einzahlen(50)
print(ben)    # Konto von Ben: -250 Euro (Dispo 500 Euro)
```

- **Überschreiben (Overriding):** Die Unterklasse schreibt eine Methode mit **gleichem Namen und gleichen
  Parametern**; für Girokonten ersetzt sie die Version der Oberklasse.
- **`super().methode()`** ruft die Version der Oberklasse auf → geerbtes Verhalten **ergänzen**; der gemeinsame
  Text steht weiter nur in `Konto`.
- **Methodensuche (MRO):** Python sucht zuerst in der Klasse des Objekts, dann in den Oberklassen, zuletzt in
  `object`; Reihenfolge in `Girokonto.__mro__` → `Girokonto, Konto, object`. `ben.abheben` → in `Girokonto`
  gefunden; `ben.einzahlen` → erst in `Konto`; `super().__str__()` sucht **ab der Oberklasse**;
  `ben.zinsen_gutschreiben()` → nirgends → `AttributeError` (ty findet das vorher).
- **`@override`** (aus `typing`, entspricht `@Override`): ty meldet `invalid-explicit-override`, wenn die Methode
  nichts überschreibt – z. B. Tippfehler `abhebn`. Ohne `@override` wäre `abhebn` still eine neue Methode und das
  Girokonto hebt ohne Dispo ab. Python selbst ignoriert die Markierung. Gegenstück: **`@final`** → ty meldet
  `override-of-final-method`.

**Sinnvoll oder nicht?** Geerbte Methoden benutzen, mit `@override` überschreiben, Eigenes ergänzen: sehr sinnvoll.
`super().__init__(…)`: **Pflicht**, sobald die Unterklasse ein eigenes `__init__` hat. `_attribute` der Oberklasse
direkt ändern: erlaubt, aber mit Vorsicht (Abhängigkeit vom Innenleben). Oberklasse über Setter statt
`super().__init__` füllen: schlechter Stil (Objekt eine Zeit lang halb fertig). Ein Attribut der Oberklasse mit
anderer Bedeutung neu belegen: vermeiden – **in Python gibt es nur ein Attribut im Objekt**, Ober- und
Unterklasse schreiben in dasselbe (Java: zwei getrennte Felder, Shadowing).

| | Überladen (Overloading) | Überschreiben (Overriding) |
|---|---|---|
| Wo? | dieselbe Klasse | Ober- und Unterklasse |
| Parameter | verschieden | gleich |
| Java | ja, Auswahl beim Übersetzen | ja, Auswahl beim Ausführen |
| Python | **gibt es nicht** (zweite `def` ersetzt die erste; Standardwerte) | ja, Auswahl beim Ausführen nach Klasse des Objekts |

### Polymorphie
**Polymorphie** (Vielgestaltigkeit): **Derselbe Methodenaufruf** führt je nach Klasse des Objekts zu
**unterschiedlichem Verhalten**. Beispiel Onlineshop: `zahlungsart.bezahlen(betrag)` bucht bei der Kreditkarte ab,
läuft über PayPal oder erstellt eine Rechnung. Der Kassencode unterscheidet die Zahlungsarten nicht.

```python
class Zahlungsart:
    def bezahlen(self, betrag: Decimal) -> str:
        return f"{betrag} Euro bezahlt"

class Kreditkarte(Zahlungsart):
    def __init__(self, nummer: str) -> None:
        self.nummer = nummer
    @override
    def bezahlen(self, betrag: Decimal) -> str:
        return f"{betrag} Euro von Karte ...{self.nummer[-4:]} abgebucht"

class Rechnungskauf(Zahlungsart):
    @override
    def bezahlen(self, betrag: Decimal) -> str:
        return f"Rechnung über {betrag} Euro, zahlbar in 14 Tagen"

def kasse(zahlungsart: Zahlungsart, betrag: Decimal) -> None:   # kennt nur die Oberklasse
    print(zahlungsart.bezahlen(betrag))

kasse(Kreditkarte("4111111111111234"), Decimal("49.90"))  # 49.90 Euro von Karte ...1234 abgebucht
kasse(Rechnungskauf(), Decimal("199.00"))                 # Rechnung über 199.00 Euro, zahlbar in 14 Tagen
```

- **Typangabe vs. Objekt:** Die Typangabe `Zahlungsart` legt fest, **was ty erlaubt** (nur, was jede Zahlungsart
  hat): `zahlungsart.nummer` → ty `unresolved-attribute`. Das **Objekt** legt beim Ausführen fest, **welches**
  `bezahlen()` läuft. Nach `if isinstance(zahlungsart, Kreditkarte):` erlaubt ty `nummer` – kein Cast wie in Java.
- **Erweiterbar:** Neue Unterklasse `Lastschrift(Zahlungsart)` → `kasse()` bleibt **unverändert** und kann sie
  sofort verarbeiten (`20.00 Euro von IBAN ...3000 eingezogen`).
- **Duck Typing:** Python prüft beim Ausführen nur, **ob die Methode da ist** („Wenn es aussieht wie eine Ente und
  quakt wie eine Ente …“). Ein `Gutschein` ohne Vererbung, aber mit `bezahlen()`, läuft; **ty** meldet aber
  `invalid-argument-type`. In der Vorlesung erben wir deshalb von `Zahlungsart`.

### `object` und abstrakte Klassen
- **Jede Klasse erbt von `object`** (Java: `Object`), auch ohne Angabe: `Konto.__bases__` → `(<class 'object'>,)`.
  Von dort stammen Standardfassungen von `__str__`, `__repr__`, `__eq__` (Ausgabe `<__main__.Leer object at 0x…>`,
  `Leer() == Leer()` → `False`). Wer in VL05 `__str__` geschrieben hat, hat also schon **überschrieben**.
- **Vereinbarung für `__repr__`** (Format wie `@dataclass`), passt dank `type(self).__name__` auch für
  Unterklassen:

```python
    @override
    def __repr__(self) -> str:
        return (f"{type(self).__name__}(inhaber={self.inhaber!r}, "
                f"kontostand={self.kontostand})")
# repr(anna) → Sparkonto(inhaber='Anna', kontostand=1530)
```

**Abstrakte Klassen:** Eine „Zahlungsart an sich“ gibt es nicht. Eine abstrakte Klasse erbt von **`ABC`** (Modul
`abc`), hält das Gemeinsame fest und dient als Grundlage; **von ihr entstehen keine Objekte**.

```python
from abc import ABC, abstractmethod

class Zahlungsart(ABC):
    @abstractmethod
    def bezahlen(self, betrag: Decimal) -> str:
        """Jede konkrete Zahlungsart muss das umsetzen."""   # kein echter Rumpf (Docstring oder ...)

    def beleg(self, betrag: Decimal) -> str:                  # konkret, für alle gleich
        return f"Beleg: {self.bezahlen(betrag)}"              # ruft das jeweilige bezahlen()

Rechnungskauf().beleg(Decimal("80.00"))  # 'Beleg: Rechnung über 80.00 Euro, zahlbar in 14 Tagen'
Zahlungsart()  # TypeError: Can't instantiate abstract class Zahlungsart without an
               # implementation for abstract method 'bezahlen'   (ty meldet es schon vorher)
```

- `@abstractmethod` legt fest, **dass** es die Methode geben muss, nicht **wie** sie arbeitet.
- Eine Unterklasse, die **nicht alle** abstrakten Methoden überschreibt, **bleibt abstrakt**:
  `PayPal("anna@example.com")` ohne `bezahlen()` → derselbe `TypeError` (schon beim Erzeugen, nicht erst beim
  Aufruf).
- Abstrakte und konkrete Methoden dürfen gemischt werden; eine konkrete Methode darf eine abstrakte aufrufen.

### Fähigkeiten statt Interfaces
Beispiel Dokumentenverwaltung: Rechnung, Lieferschein, Mahnung, Newsletter **sind** Dokumente (Kategorie →
Oberklasse). Manche **können** gedruckt, manche versendet werden, manche beides (Fähigkeiten, quer durch die
Klassen). Java erlaubt nur eine Oberklasse und beschreibt Fähigkeiten mit **Interfaces** (Vertrag: Klasse
verspricht bestimmte Methoden). **Python hat kein `interface`**: Eine Fähigkeit ist eine **abstrakte Klasse mit nur
abstrakten Methoden** (ohne Attribute, ohne Konstruktor), und Python erlaubt **mehrere Oberklassen** – statt
`implements` stehen die Fähigkeiten mit in der Klammer.

```python
class Druckbar(ABC):
    @abstractmethod
    def drucken(self) -> None: ...

class Versendbar(ABC):
    @abstractmethod
    def versenden(self, email: str) -> None: ...

class Dokument:                                   # Kategorie: Attribut + Konstruktor
    def __init__(self, nummer: str) -> None:
        self.nummer = nummer

class Rechnung(Dokument, Druckbar, Versendbar):   # erst Kategorie, dann Fähigkeiten
    @override
    def drucken(self) -> None:
        print(f"Rechnung {self.nummer} wird gedruckt")
    @override
    def versenden(self, email: str) -> None:
        print(f"Rechnung {self.nummer} geht an {email}")

class Lieferschein(Dokument, Druckbar):
    @override
    def drucken(self) -> None:
        print(f"Lieferschein {self.nummer} wird gedruckt")

for dokument in [Rechnung("R-1001"), Lieferschein("L-2001")]:   # ablage: list[Dokument]
    if isinstance(dokument, Druckbar):
        dokument.drucken()
    if isinstance(dokument, Versendbar):
        dokument.versenden("einkauf@kunde.de")
# Rechnung R-1001 wird gedruckt
# Rechnung R-1001 geht an einkauf@kunde.de
# Lieferschein L-2001 wird gedruckt
```

`isinstance()` funktioniert mit Fähigkeiten wie mit Kategorien; danach weiß ty, dass `drucken()` da ist. Ohne die
Prüfung gäbe es beim Lieferschein einen `AttributeError`. Eine neue Klasse `Mahnung` fügt sich ohne Änderung der
Schleife ein. Mehrere Oberklassen nutzen wir **nur für solche Fähigkeiten**.
(`Rechnung.__mro__` → `Rechnung, Dokument, Druckbar, Versendbar, ABC, object`, selbst nachgeprüft.)

| | Abstrakte Klasse (Kategorie) | Fähigkeit (Interface) |
|---|---|---|
| Beziehung | „ist ein …“ | „kann …“ |
| Java | `abstract class`, `extends` | `interface`, `implements` |
| Python | Klasse mit `ABC` | Klasse mit `ABC`, nur abstrakte Methoden |
| Objekte erzeugen? | nein | nein |
| Methoden | konkrete und abstrakte | nur abstrakte |
| Attribute, Konstruktor | ja | nein |
| wie viele je Klasse? | eine | beliebig viele |

Ausblick auf der Folie: **`typing.Protocol`** – eine Klasse erfüllt ein Protocol schon, wenn sie die Methoden hat,
**ohne zu erben** (Duck Typing, das ty prüfen kann).

## Wichtige Begriffe

- **Klasse** – Bauplan für Objekte (Attribute + Methoden), Name in PascalCase
- **Objekt / Instanz** – konkretes Exemplar einer Klasse mit eigenen Attributwerten
- **Attribut / Instanzattribut** – Datum eines Objekts (`self.kontostand`), beschreibt den Zustand
- **Methode** – Funktion in der Klasse, erster Parameter `self`; beschreibt das Verhalten
- **`self`** – das Objekt vor dem Punkt; `anna.einzahlen(50)` = `Konto.einzahlen(anna, 50)` (Java: `this`)
- **Konstruktor `__init__`** – läuft beim Erzeugen, setzt den Anfangszustand, gibt `None` zurück
- **Dunder-Methoden** – `__init__`, `__str__`, `__repr__`, `__eq__` … mit fester Bedeutung
- **`__str__` / `__repr__`** – Ausgabe für Menschen (`print`) / für Entwickler (REPL, Listen)
- **UML-Klassendiagramm** – Kasten mit Name, Attributen, Methoden
- **Identität vs. Gleichheit** – `is` (dasselbe Objekt) vs. `==` (ohne `__eq__` ebenfalls Identität)
- **Klassenattribut** – im Klassenrumpf, einmal pro Klasse (Java: `static`); ändern über `Klasse.attr`
- **Kapselung** – Objekt schützt seinen Zustand und zeigt nur das Nötige
- **`_name` / `__name`** – Konvention „intern“ / Name Mangling (`_Konto__name`), beides kein echter Schutz
- **Property (`@property`, `@x.setter`)** – Methode, die wie ein Attribut benutzt wird; Setter prüft Werte
- **Hat-ein-Beziehung (Komposition)** – Objekt als Attribut eines anderen
- **Modul / Paket** – `.py`-Datei / Ordner mit `__init__.py`
- **`@dataclass`** – erzeugt `__init__`, `__repr__`, `__eq__` aus annotierten Attributen
- **Vererbung, Ober-/Unterklasse** – „ist ein“, `class Unter(Ober):`
- **`super()`** – Zugriff auf die Oberklasse: `super().__init__(…)`, `super().methode()`
- **Überschreiben (Overriding)** – gleiche Methode in der Unterklasse ersetzt die der Oberklasse
- **`@override` / `@final`** – Markierungen aus `typing`, nur von ty geprüft
- **MRO (`__mro__`)** – Suchreihenfolge für Methoden, endet bei `object`
- **`isinstance` / `issubclass` / `type`** – Klasse inkl. Oberklassen / Klassenbeziehung / genaue Klasse
- **Polymorphie** – derselbe Aufruf, unterschiedliches Verhalten je nach Klasse des Objekts
- **Duck Typing** – nur zählt, ob die Methode da ist, nicht die Klasse
- **`object`** – Wurzel aller Klassen
- **Abstrakte Klasse (`ABC`) / abstrakte Methode (`@abstractmethod`)** – keine Objekte; Pflicht für Unterklassen
- **Fähigkeit / Interface** – abstrakte Klasse nur mit abstrakten Methoden, „kann …“, mehrere je Klasse
- **Mehrfachvererbung** – mehrere Oberklassen, in der Vorlesung nur für Fähigkeiten
- **`typing.Protocol`** – Interface ohne Vererbung (strukturelle Typprüfung)

## Typische Fehler / Fallen

- **`self` vergessen** – in der Parameterliste (`TypeError`: ein Argument zu viel) oder vor dem Attribut
  (`kontostand += betrag` statt `self.kontostand += betrag` → lokale Variable/`UnboundLocalError`).
- **`new Konto(...)`** gibt es nicht; `Konto.__init__("Anna", 100)` ist kein Objekterzeugen.
- **Zwei `__init__`** – das zweite ersetzt das erste; Varianten nur über Standardwerte.
- **`konto2 = konto1` ist keine Kopie** – Änderungen über beide Namen sichtbar.
- **`==` bei eigenen Klassen** vergleicht ohne `__eq__` nur die Identität → zwei gleiche Konten sind `False`;
  bei `@dataclass` dagegen `True` (aber `is` bleibt `False`).
- **Tippfehler bei Attributzuweisung** (`anna.kontostnad = 500`) legt still ein neues Attribut an – nur ty meldet es.
- **Klassenattribut über `self`/Objekt ändern** legt ein Instanzattribut an; Klassenzähler bleibt stehen. Immer
  `Klasse.attribut += 1`.
- **`_attribut` ist kein Schutz**, `__attribut` auch nicht (nur Umbenennung).
- **Property ohne Setter zuweisen** → `AttributeError`; Property mit Klammern aufrufen (`lena.jahresgehalt()`) →
  `TypeError: 'int' object is not callable`.
- **Setter in `__init__` umgehen** (`self._preis = preis` statt `self.preis = preis`) → Regel gilt beim Anlegen
  nicht.
- **Leere Liste als Parameter-Standardwert** statt in `__init__` (`positionen: list = []`) → geteilt zwischen
  Objekten (VL04).
- **`super().__init__(…)` vergessen** → `AttributeError` erst beim ersten Zugriff; **ty meldet es nicht**.
- **Vererbung für „hat ein“** (Konto erbt von Kunde) – falsches Werkzeug, Attribut verwenden.
- **Methodenname beim Überschreiben vertippt** → still neue Methode; `@override` macht es für ty sichtbar.
- **Zugriff auf Unterklassen-Attribut über Oberklassen-Typ** (`zahlungsart.nummer`) → ty-Fehler; vorher
  `isinstance()`.
- **Abstrakte Klasse instanziieren** oder Unterklasse ohne alle abstrakten Methoden → `TypeError` schon beim
  Erzeugen.
- **`type(x) is Konto`** ist bei Unterklassen `False` – für „ist ein“ `isinstance` benutzen.
- **Duck Typing** läuft zur Laufzeit, ty meldet aber `invalid-argument-type`.
- **Überladen ≠ Überschreiben** – Klassiker in Klausuren; Python kennt nur Überschreiben.
