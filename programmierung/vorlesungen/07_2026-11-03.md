### Teil 1: Polymorphie (VL06 Folien 30–40)

Einstiegsfrage: *„Sie klicken im Onlineshop auf ‚Jetzt bezahlen‘. Was muss der Shop je nach Zahlungsart tun?“*

**Was ist das?** Polymorphie (griechisch „Vielgestaltigkeit“) heißt: **Dieselbe Zeile Code** macht je nach Objekt
**etwas anderes**. Vorbild aus dem Alltag: Du sagst zu jedem Tier „Mach dein Geräusch!“ – der Hund bellt, die Katze
miaut. Du musst nicht wissen, welches Tier vor dir steht.

Im Shop: Die Kasse ruft immer `zahlungsart.bezahlen(betrag)` auf. Ist es eine Kreditkarte, wird abgebucht; ist es
ein Rechnungskauf, wird eine Rechnung erstellt.

```python
from decimal import Decimal
from typing import override

class Zahlungsart:
    def bezahlen(self, betrag: Decimal) -> str:
        return f"{betrag} Euro bezahlt"

class Kreditkarte(Zahlungsart):
    def __init__(self, nummer: str) -> None:
        self.nummer = nummer

    @override
    def bezahlen(self, betrag: Decimal) -> str:
        return f"{betrag} Euro von Karte ...{self.nummer[-4:]} abgebucht"

class Rechnungskauf(Zahlungsart):
    @override
    def bezahlen(self, betrag: Decimal) -> str:
        return f"Rechnung über {betrag} Euro, zahlbar in 14 Tagen"

def kasse(zahlungsart: Zahlungsart, betrag: Decimal) -> None:
    print(zahlungsart.bezahlen(betrag))      # immer dieselbe Zeile

kasse(Kreditkarte("4111111111111234"), Decimal("49.90"))  # 49.90 Euro von Karte ...1234 abgebucht
kasse(Rechnungskauf(), Decimal("199.00"))                 # Rechnung über 199.00 Euro, zahlbar in 14 Tagen
```

Wie findet Python die richtige Methode? Genau wie bei Termin 6 (Methodensuche): erst in der **Klasse des Objekts**
schauen, dann in der Oberklasse. Bei der Kreditkarte findet Python `bezahlen` schon in `Kreditkarte`.

**Nutzen (Folie 35):** Kommt eine neue Zahlungsart dazu (`Lastschrift` mit IBAN → `20.00 Euro von IBAN ...3000
eingezogen`), schreibt man nur eine neue Unterklasse. `kasse()` bleibt **unverändert**.

**Typangabe vs. Objekt – wer entscheidet was? (Folie 34)**

- Die **Typangabe** (`zahlungsart: Zahlungsart`) entscheidet, was **ty erlaubt**: nur das, was *jede* Zahlungsart
  hat. `zahlungsart.bezahlen(...)` ist ok, `zahlungsart.nummer` → ty-Fehler `unresolved-attribute` (ein
  Rechnungskauf hat keine Kartennummer).
- Das **Objekt** entscheidet beim Ausführen, **welches** `bezahlen()` läuft.
- Braucht man doch die Nummer: erst prüfen. Danach weiß ty Bescheid, ein Cast wie in Java ist nicht nötig.

```python
if isinstance(zahlungsart, Kreditkarte):
    print(zahlungsart.nummer)   # jetzt ok
```

**Duck Typing (Folie 39):** Python selbst prüft beim Ausführen nur, **ob die Methode da ist** – nicht, von welcher
Klasse das Objekt stammt („Wenn es aussieht wie eine Ente und quakt wie eine Ente, ist es eine Ente“). Ein
`Gutschein`, der **nicht** von `Zahlungsart` erbt, aber `bezahlen()` hat, läuft also: `15.00 Euro mit Gutschein
bezahlt`. **ty** meldet aber `invalid-argument-type`, weil die Typangabe `Zahlungsart` verlangt. Deshalb in der
Vorlesung: immer von `Zahlungsart` erben – dann prüft ty mit und jeder sieht die Absicht.

### Teil 2: `object`, `__repr__` und abstrakte Klassen (Folien 42–47)

**`object` = Wurzel aller Klassen.** Jede Klasse erbt von `object`, auch ohne Klammer (`Konto.__bases__` →
`(<class 'object'>,)`). Von dort kommen schlichte Standardversionen von `__str__`, `__repr__`, `__eq__`:

```python
class Leer:
    pass

print(Leer())            # <__main__.Leer object at 0x102e48980>   (Klasse + Speicheradresse)
print(Leer() == Leer())  # False – Standard-== vergleicht nur, ob es dasselbe Objekt ist
```

Wer in VL05 `__str__` geschrieben hat, hat also schon eine Methode von `object` **überschrieben**.

**`__repr__`-Vereinbarung (Folie 43):** Format wie bei `@dataclass`: `Klassenname(attribut=wert, …)`.
`__str__` ist für Menschen (Kontoauszug), `__repr__` für Entwickler (Fehlersuche).

```python
@override
def __repr__(self) -> str:
    return (
        f"{type(self).__name__}(inhaber={self.inhaber!r}, "
        f"kontostand={self.kontostand})"
    )
# in Konto geschrieben, für ein Sparkonto-Objekt: Sparkonto(inhaber='Anna', kontostand=1530)
```

- `type(self).__name__` = Name der **tatsächlichen** Klasse → passt automatisch auch für Unterklassen.
- `!r` setzt Texte in Anführungszeichen (`'Anna'`), Zahlen bleiben ohne.
- Gibt es kein eigenes `__str__`, nimmt `print()` das `__repr__`.

**Abstrakte Klassen (Folien 44–46).** Frage in die Runde: *„Was sollte `Zahlungsart().bezahlen(…)` eigentlich
tun?“* – Antwort: nichts Sinnvolles. Eine „Zahlungsart an sich“ gibt es nicht, nur Kreditkarte, Rechnung usw.
`Zahlungsart` ist eine **Abstraktion**: Sie sagt, was alle gemeinsam haben, und lässt Details weg.

**Was ist das?** Eine abstrakte Klasse ist wie ein **Formular mit Pflichtfeldern**: Sie legt fest, *welche*
Methoden jede Unterklasse haben **muss**, aber nicht *wie* sie arbeiten. Von der abstrakten Klasse selbst kann man
**keine Objekte** erzeugen.

```python
from abc import ABC, abstractmethod

class Zahlungsart(ABC):                        # erbt von ABC → abstrakt
    @abstractmethod
    def bezahlen(self, betrag: Decimal) -> str:
        """Jede konkrete Zahlungsart muss das umsetzen."""   # kein echter Rumpf nötig

    def beleg(self, betrag: Decimal) -> str:   # konkrete Methode: für alle gleich
        return f"Beleg: {self.bezahlen(betrag)}"

class Rechnungskauf(Zahlungsart):
    @override
    def bezahlen(self, betrag: Decimal) -> str:
        return f"Rechnung über {betrag} Euro, zahlbar in 14 Tagen"

print(Rechnungskauf().beleg(Decimal("80.00")))
# Beleg: Rechnung über 80.00 Euro, zahlbar in 14 Tagen
Zahlungsart()
# TypeError: Can't instantiate abstract class Zahlungsart
# without an implementation for abstract method 'bezahlen'
```

- ty meldet `Zahlungsart()` **schon vor dem Start** („Cannot instantiate abstract class“), Python erst beim Ausführen.
- Eine Unterklasse, die **nicht alle** abstrakten Methoden überschreibt, bleibt selbst abstrakt
  (`PayPal("anna@example.com")` ohne `bezahlen` → derselbe `TypeError` für `PayPal`).
- Abstrakte und konkrete Methoden dürfen gemischt werden; die konkrete `beleg()` ruft das jeweilige `bezahlen()`
  auf (wieder Polymorphie).
- Java: `abstract class` / `extends`. Python: `class X(ABC)` + `@abstractmethod` aus dem Modul `abc`.

### Teil 3: Fähigkeiten statt Interfaces (Folien 49–56)

**Problem:** Ein Unternehmen hat Dokumente (Rechnung, Lieferschein, Newsletter). „Ist ein Dokument“ ist eine
**Kategorie** → Oberklasse. Aber „kann gedruckt werden“ / „kann per E-Mail versendet werden“ sind **Fähigkeiten**,
die quer durch die Klassen gehen: Rechnung kann beides, Lieferschein nur drucken, Newsletter nur versenden.

- Java: nur **eine** Oberklasse, Fähigkeiten als `interface` mit `implements`.
- Python: kein `interface`-Schlüsselwort. Eine Fähigkeit ist eine **abstrakte Klasse mit nur abstrakten Methoden**
  (keine Attribute, kein `__init__`). Python erlaubt **mehrere Oberklassen** – die Fähigkeiten stehen einfach mit
  in der Klammer.

```python
class Druckbar(ABC):
    @abstractmethod
    def drucken(self) -> None: ...

class Versendbar(ABC):
    @abstractmethod
    def versenden(self, email: str) -> None: ...

class Dokument:                                    # Kategorie: hat Attribut + Konstruktor
    def __init__(self, nummer: str) -> None:
        self.nummer = nummer

class Rechnung(Dokument, Druckbar, Versendbar):    # ist ein Dokument, kann drucken + versenden
    @override
    def drucken(self) -> None:
        print(f"Rechnung {self.nummer} wird gedruckt")

    @override
    def versenden(self, email: str) -> None:
        print(f"Rechnung {self.nummer} geht an {email}")

class Lieferschein(Dokument, Druckbar):            # kann nur drucken
    @override
    def drucken(self) -> None:
        print(f"Lieferschein {self.nummer} wird gedruckt")
```

**Fähigkeit prüfen mit `isinstance()` (Folien 52–55):**

```python
ablage: list[Dokument] = [Rechnung("R-1001"), Lieferschein("L-2001")]
for dokument in ablage:
    if isinstance(dokument, Druckbar):
        dokument.drucken()
    if isinstance(dokument, Versendbar):
        dokument.versenden("einkauf@kunde.de")
```

Runde für Runde:

| Runde | `dokument` | `Druckbar`? | `Versendbar`? |
|---|---|---|---|
| 1 | Rechnung R-1001 | True → „Rechnung R-1001 wird gedruckt“ | True → „Rechnung R-1001 geht an einkauf@kunde.de“ |
| 2 | Lieferschein L-2001 | True → „Lieferschein L-2001 wird gedruckt“ | False → nichts |

Ohne die zweite Prüfung gäbe es in Runde 2 einen `AttributeError` (Lieferschein hat kein `versenden`). Kommt eine
neue Klasse `Mahnung` dazu, bleibt die Schleife unverändert.

**Abstrakte Klasse oder Fähigkeit? (Folie 56)**

- **Abstrakte Klasse (Kategorie):** „ist ein …“; konkrete **und** abstrakte Methoden; Attribute und Konstruktor
  erlaubt; **eine** pro Klasse; Java `abstract class`/`extends`.
- **Fähigkeit (Interface):** „kann …“; **nur** abstrakte Methoden; keine Attribute, kein Konstruktor; **beliebig
  viele** pro Klasse; Java `interface`/`implements`.
- Gemeinsam: Von beiden kann man **keine Objekte** erzeugen; beide erben von `ABC`.
- Ausblick: `typing.Protocol` – eine Klasse erfüllt es schon, wenn sie die Methoden hat, ohne zu erben (Duck Typing,
  das ty prüfen kann). Mehrere Oberklassen nutzt die Vorlesung **nur** für Fähigkeiten.

```python
def hinzufuegen(self, produkt: Produkt, menge: int) -> bool:
    schon_im_korb = 0
    for position in self.positionen:            # gibt es das Produkt schon im Korb?
        if position.produkt is produkt:
            schon_im_korb = position.menge
    if schon_im_korb + menge > produkt.bestand:
        return False                            # main.py gibt die Meldung aus
    for position in self.positionen:
        if position.produkt is produkt:
            position.menge += menge             # vorhandene Position erhöhen
            return True
    self.positionen.append(Position(produkt, menge))   # sonst neue Position
    return True
```

Runde für Runde bei „erst 3, dann noch 1 French Press“ (Bestand 3):

| Aufruf | `schon_im_korb` | Prüfung `schon + menge > 3` | Ergebnis |
|---|---|---|---|
| `hinzufuegen(fp, 3)`, Korb leer | 0 (Schleife läuft 0-mal) | 0 + 3 > 3 → False | neue Position (3) → `True` |
| `hinzufuegen(fp, 1)` | 3 (Runde 1: Position ist French Press) | 3 + 1 > 3 → True | `False`, abgelehnt |

## Wichtige Begriffe

- **Polymorphie** – derselbe Methodenaufruf, unterschiedliches Verhalten je nach Klasse des Objekts
- **Typangabe vs. Objekt** – Typangabe: was ty erlaubt; Objekt: welche Methode beim Ausführen läuft
- **Duck Typing** – Python prüft nur, ob die Methode existiert, nicht die Klasse; ty prüft die Typangabe
- **`object`** – Wurzel jeder Klasse; liefert Standard-`__str__`, `__repr__`, `__eq__`
- **`__repr__`** – Beschreibung für Entwickler, Format `Klasse(attr=wert)`; `type(self).__name__`, `!r`
- **Abstrakte Klasse** – erbt von `ABC`, keine Objekte möglich, Vorlage für Unterklassen
- **`@abstractmethod`** – Pflichtmethode ohne echten Rumpf; jede konkrete Unterklasse muss sie überschreiben
- **Konkrete Klasse** – Klasse, von der man Objekte erzeugen kann (alle abstrakten Methoden umgesetzt)
- **Fähigkeit (Interface)** – abstrakte Klasse nur mit abstrakten Methoden, „kann …“
- **Mehrfachvererbung** – `class Rechnung(Dokument, Druckbar, Versendbar)`; in der VL nur für Fähigkeiten
- **`typing.Protocol`** – Ausblick: Fähigkeit ohne Erben, von ty geprüft
- **Pair Programming** – zu zweit an einem Rechner, Rollen tippen/mitdenken wechseln
- **`Produkt | None`** – Rückgabetyp „entweder Produkt oder nichts“ (bei `finden`)

**A3 – Abstrakte Klasse**

```python
from abc import ABC, abstractmethod

class Tier(ABC):
    @abstractmethod
    def laut(self) -> str: ...
    def vorstellen(self) -> str:
        return "Ich sage " + self.laut()

class Hund(Tier):
    def laut(self) -> str:
        return "Wuff"

class Katze(Tier):
    pass

print(Hund().vorstellen())
print(Katze().vorstellen())
```

*Lösung:* Zeile 1: `Ich sage Wuff` (`vorstellen` aus `Tier`, `laut` aus `Hund` – Polymorphie). Zeile 2:

also abstrakt. ty meldet das schon vor dem Start.

**A4 – Fähigkeiten mit `isinstance`**

```python
class Geraet:
    def __init__(self, name: str) -> None:
        self.name = name

class Aufladbar(ABC):
    @abstractmethod
    def aufladen(self) -> None: ...

class Netzwerkfaehig(ABC):
    @abstractmethod
    def verbinden(self, netz: str) -> None: ...

class Laptop(Geraet, Aufladbar, Netzwerkfaehig):
    def aufladen(self) -> None:
        print(self.name, "geladen")
    def verbinden(self, netz: str) -> None:
        print(self.name, "->", netz)

class Router(Geraet, Netzwerkfaehig):
    def verbinden(self, netz: str) -> None:
        print(self.name, "->", netz)

class Monitor(Geraet):
    pass

for g in [Laptop("Laptop"), Router("Router"), Monitor("Monitor")]:
    if isinstance(g, Aufladbar):
        g.aufladen()
    if isinstance(g, Netzwerkfaehig):
        g.verbinden("DHBW-Gast")
```

*Lösung:*

| Runde | `g` | Aufladbar? | Netzwerkfähig? | Ausgabe |
|---|---|---|---|---|
| 1 | Laptop | True | True | `Laptop geladen` und `Laptop -> DHBW-Gast` |
| 2 | Router | False | True | `Router -> DHBW-Gast` |
| 3 | Monitor | False | False | (nichts) |

Insgesamt **3 Zeilen**. Der Monitor erzeugt keine Ausgabe und auch keinen Fehler.

### VL06 Übung 3: Personalkosten für das ganze Team (`uebung3.py`, ca. 15 Min.)
(1) Klassen aus Übung 2 übernehmen; `team: list[Mitarbeiter]` mit sechs Personen (Entwickler, Manager, einfache

*Lösungshinweise:*

```python
def personalkosten(team: list[Mitarbeiter]) -> int:
    summe = 0
    for person in team:
        summe += person.monatskosten()   # Polymorphie: Manager rechnet seine Zulage selbst dazu
    return summe
```

### VL06 Übung 4: Geräteverwaltung, Teil 1 (`uebung4.py`, ca. 20 Min.)
(1) Abstrakte Klasse `Geraet` mit `hersteller`, `modell`, `baujahr: int`, konkreter Methode `einschalten()`
(`Lenovo ThinkPad T14 wird eingeschaltet.`) und abstrakter Methode `status() -> str`. (2) `__repr__` im
vereinbarten Format. (3) Unterklassen `Laptop` und `Smartphone` (`akku_prozent`) und `Router`
(`verbundene_geraete`), jede mit eigenem `status()`. (4) `inventar: list[Geraet]` mit drei Geräten; jedes ausgeben,
Status zeigen, einschalten. (5) `Geraet(…)` direkt erzeugen – was melden ty und Python? Zusatz: eigene Methoden
(`screenshot()`, `firmware_update()`) in der Schleife aufrufen – was braucht man dafür?

*Lösungshinweise:*

```python
class Geraet(ABC):
    def __init__(self, hersteller: str, modell: str, baujahr: int) -> None:
        self.hersteller = hersteller
        self.modell = modell
        self.baujahr = baujahr

    def einschalten(self) -> None:
        print(f"{self.hersteller} {self.modell} wird eingeschaltet.")

    @abstractmethod
    def status(self) -> str:
        """Jedes konkrete Gerät beschreibt seinen Zustand selbst."""

    @override
    def __repr__(self) -> str:
        return (
            f"{type(self).__name__}(hersteller={self.hersteller!r}, "
            f"modell={self.modell!r}, baujahr={self.baujahr})"
        )

class Laptop(Geraet):
    def __init__(self, hersteller: str, modell: str, baujahr: int, akku_prozent: int) -> None:
        super().__init__(hersteller, modell, baujahr)
        self.akku_prozent = akku_prozent

    @override
    def status(self) -> str:
        return f"Akku {self.akku_prozent} %"
```

- Ausgabe mit `print(geraet, "-", geraet.status())`: `Laptop(hersteller='Lenovo', modell='ThinkPad T14',
  baujahr=2023) - Akku 80 %`, dann `Lenovo ThinkPad T14 wird eingeschaltet.`; ebenso Samsung Galaxy S24 (35 %) und
  AVM FRITZ!Box 7590 (`12 Geräte verbunden`).
- `__repr__` nur **einmal** in `Geraet` – dank `type(self).__name__` steht trotzdem „Laptop“, „Router“ usw. da.
- (5) ty (laut Musterlösung): `call-non-callable: Cannot instantiate abstract class` `Geraet`; Python: `TypeError: Can't instantiate abstract class Geraet
  without an implementation for abstract method 'status'`.
- Zusatz: In einer `list[Geraet]` kennt ty nur, was **jedes** Gerät hat → vorher `if isinstance(geraet,
  Smartphone): geraet.screenshot()`.

### VL06 Übung 5: Geräteverwaltung, Teil 2 (`uebung5.py`, ca. 20 Min.)
(1) Fähigkeiten `Aufladbar` (`aufladen()`) und `Netzwerkfaehig` (`verbinden(netzwerk)`). (2) Laptop und
Smartphone können beides, Router nur Netzwerk; `aufladen()` setzt den Akku auf 100 %, `verbinden()` gibt z. B.
`Lenovo ThinkPad T14 ist mit DHBW-Gast verbunden.` aus. (3) `Monitor` ohne Fähigkeiten. (4) Schleife: aufladbare
laden, netzwerkfähige mit `"DHBW-Gast"` verbinden, danach alle mit Status ausgeben. Zusatz:
`alle_aufladen(inventar) -> int` gibt zurück, wie viele geladen wurden.

*Lösungshinweise:*

```python
class Aufladbar(ABC):
    @abstractmethod
    def aufladen(self) -> None: ...

class Laptop(Geraet, Aufladbar, Netzwerkfaehig):   # Kategorie zuerst, dann Fähigkeiten
    ...
    @override
    def aufladen(self) -> None:
        self.akku_prozent = 100

class Monitor(Geraet):                              # kein eigenes __init__ → das von Geraet wird geerbt
    @override
    def status(self) -> str:
        return "angeschlossen"

for geraet in inventar:
    if isinstance(geraet, Aufladbar):
        geraet.aufladen()
    if isinstance(geraet, Netzwerkfaehig):
        geraet.verbinden("DHBW-Gast")
```

## Typische Fehler / Fallen

- **Attribut einer Unterklasse über die Oberklassen-Typangabe benutzen** (`zahlungsart.nummer`) → ty-Fehler;
  erst `isinstance` prüfen.
- **Duck Typing heißt nicht „ty ist egal“:** Programm läuft, ty meldet trotzdem `invalid-argument-type`.
- **Abstrakte Klasse ohne `ABC`** (`class Geraet:` mit `@abstractmethod`) → Python verhindert dann das Erzeugen
  **nicht**. Beides gehört zusammen: `(ABC)` **und** `@abstractmethod`.
- **Eine abstrakte Methode vergessen umzusetzen** → `TypeError` beim **Erzeugen** des Objekts, nicht beim Aufruf.
- **Fehler „kommt erst beim Aufruf“ erwarten** – falsch, er kommt bei `Katze()`.
- **Fähigkeit mit Attributen/`__init__`** – laut Vorlesung haben Fähigkeiten nur abstrakte Methoden.
- **Mehrfachvererbung für „hat ein“** – nur für Fähigkeiten verwenden.
- **`isinstance`-Prüfung vergessen**, bevor man eine Fähigkeits-Methode aufruft → `AttributeError`
  (Lieferschein hat kein `versenden`).
- **`__repr__` mit festem Klassennamen** (`"Geraet(…)"`) statt `type(self).__name__` → falsche Ausgabe für Unterklassen.
- **Kaffeeshop:** schon im Korb liegende Menge nicht mitzählen; zweite Position statt Menge erhöhen;
  `korb.positionen.clear()` leert auch die Bestellung (Stufe 2).
